# 复盘：2026-11-11 更新事故（用户升级后身份与小组「丢失」）

> 结论：数据没丢，是设备的「身份」跟着 origin 走了。公开包在 1.3.8 ~ 1.5.2 期间默认打开测试站，
> 用户升级后浏览器换了一个 origin，看不见原来在正式站上的令牌；服务端 D1 里的账号、小组、快照一直都在。

## 2. 根因

1. **清单与包解耦缺失**：1.3.8 ~ 1.5.2 的公开清单指向的包，默认站是测试站。内测期的默认站改动
   随公开分发外泄，用户升级即被换 origin。
2. **回滚只回网页**：11-10 的回滚只把网页退回旧部署，下载站 `latest.apk` 与两份清单没动，
   用户仍然会升到有问题的包；「网页旧、清单新、包新」是最坏组合。
3. **没有通道断言**：构建期不校验「包默认站 == 通道默认站」，发版期不校验「正式清单只指向正式包」，
   错误可以一路到线上都没有机械拦截。
4. **没有身份找回机制**：origin 切换后没有任何提示、出口或救援；恢复码虽然跨站有效，
   但用户不知道自己「换了站」，也没有人引导。

## 3. 我方的判断失误

| 失误 | 后果 | 纠正 |
|---|---|---|
| 先提出 C 方案（壳层跨 origin 自动搬凭据） | 方向反了：等于把公开用户搬进测试站，让测试站变正式站 | 用户叫停，改为「公开包默认站回正式站」 |
| 多次让用户自己操作（自救指引、连点版本号切服） | 普通用户不会做，也解释不了「为什么是我」；最终作废 | 改为服务端识别 + 运维重置恢复码，直接发码 |
| 把「升级后仍为空」先归因于服务器偏好覆盖 | 实际偏好只有用户主动切服才会写，壳不会自动写；解释不成立 | 用户质疑后重新核查，确认是默认站翻转导致 origin 变化 |
| 把「改默认站点」当成改常量 | 没有按数据迁移评估影响人群与找回路径 | 写入《发版与更新规范》「铁律」一节 |

## 5. 以后怎么避免

- 任何「默认站点」改动，先写迁移评估：影响哪些人、他们的数据在哪个 origin、怎么找回、要不要救援。
- 发版三件套顺序固定：包 → 清单 → 网页；回滚同样三件一起回。
- 发版前必须看到构建期的 `[通道校验]` 与 `[签名校验]` 输出，发版时必须看到 `deploy-web.mjs` 的清单断言。
- 内测功能只走内测通道；正式网页的 bundle 断言不放松。
- 出问题先查《发版与更新规范》「一页速查」的五项，不先猜。
