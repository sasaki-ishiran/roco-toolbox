## 0. 已定口径

1. 撮合层多对多，成交层恒为一对一。
2. 不做积分、不做货币；保留市场形态，不用积分结算。
3. 双路径结算：现货（一蛋换一蛋）为主，互相定制兜底；优先现货，没有现货才退定制并提示等待。
4. 蛋仓：采集时自动标注关键数据；每颗蛋记「最后确认时间」；必须有失效机制；按新鲜度加权。
5. 第三方巡检统一订阅，用户无感；三道护栏：每日配额、按账号合并并缓存、失败静默降级。
6. 赞助整段搁置，连入口都不留；配额、缓存、降级三道护栏保留。
7. 三方环形撮合不做，连「发现提示」也不做。
8. 交付侧是设计重心：交付必须双方同时在线，撮合输出要包含交接信息（带什么、去哪、几点、谁先给）。
9. 供给按现有形式发布到组内，不另建可见性模型。
10. 「我要」直接复用用户已设的计划，不新建偏好字段；不使用「最低接受」这类措辞。
11. 旧需求中心走改造、融入目标形态、可退回。
12. 挡位只做标注，不做计价。
13. 家园状态更新两套并存：手动刷新采集 = 用户声明，作为进度事件立刻让对方可见；订阅巡检 = 系统快照，只更新「最后确认时间」。两者分开记录、界面分开表述。
14. 多人满足规则为**接受式**：不做抢占，需求带数量，满足即关。
15. 不做同蛋组通配：用户要什么就发什么，我们只在用户选择之前给推荐。
16. 归属由平台自动匹配（订单是平台概念，两侧数据都在平台里）；多单同时进行时提供分配页让用户指认。
17. 标注分两级来源：系统采集自动标注并打「系统确认」；用户手动标注不打标记，支持同物种批量。两边内容一致。
18. 蛋重与体型等价；体重不给精确值，只给大块头 / 小不点。
19. 性格：普通窝按父母计算概率；绿窝 100% 等于「学院小窝里那只」的性格，父母性格不同时不失效、不随机二选一。
20. 性别不标注：蛋卡与交接卡都不出现性别栏，不留占位；数据模型不为此留字段。
21. 绿窝的位置即性格选择：交接卡必须写明「哪只进绿窝」，不能只写这对亲本。
22. 需求侧也不含性别条件：需求只描述这颗蛋本身（物种、性格、体型、声音、满重档）。

## 1. 现状结论

### 1.1 两条链路的实测对照

| 环节 | 旧需求中心 | 现计划中心 |
| --- | --- | --- |
| 找需求 | 4 列小卡，约 24 张 / 屏；有搜索、需求方筛选、性格 / 体型 / 声音筛选 | 2 列大卡，约 10 张 / 屏；无搜索、无筛选 |
| 判断能不能接 | 「我能接的」是硬过滤分区 | 所有未接的都进「你能接的」，靠一行理由区分 |
| 接单 | 先看详情再接，满 / 零体重强制确认 | 卡面一键，无确认 |
| 找目标 | 详情给推荐配对 | **没有**，只说到「我的产线能补」 |
| 抓到后 | 无义务步骤 | 必须「标已上窝」，否则发布人看不到「去确认」 |
| 结单 | 系统查背包有无匹配个体，没有才问 | 一键结单，无校验；多已认领只结第一条 |
| 批量 | 勾 N 颗 → 一个弹层 → 发布，5 次点击 | 逐颗「开始 → 发需求 → 填条件 → 发布」 |

**【判定】** 点击总数接近，真正增加的是三处：扫描量、每颗蛋重复发起、抓到后的回报握手。被删掉的是旧链路里最省操作的两项：配对方案与背包校验。

### 1.2 搁置率的根因

**【判定】** 大量需求挂着没人接，根因不是人少，而是**单向**：只表达「我要」，不表达「我出」。

### 1.3 规则核实

| 项 | 结论 | 证据 |
| --- | --- | --- |
| 蛋重网格 | 254 条区间全是 0.001 kg 整数倍，0 例外 | `src/data/eggWeights.json` |
| 满重挡位 | `N = (max - big) / 0.001 + 1`，中位 21、最窄 1、最宽 1606 | 同上 |
| 最小体重挡位 | `(small - min) / 0.001 + 1`，与满重逐只对称 | 同上 |
| 数据覆盖 | 210 个图鉴蛋物种中 161 有数据、49 缺 | `catalog.gen.json` × `eggWeights.json` |
| 蛋重与体型 | **等价**：蛋判大块头 = 孵化后精灵大块头；满重只是蛋重标记 | 本轮口径 |
| 窝位 | 11 / 账号（1 学院 + 10 普通），客户端派生结构完整表达 | `demandPlacement.ts`、`nestPlan.ts` |
| 绿窝 | 1 / 账号，1 只精灵最多 2 条线 | `nestPlan.ts` |
| 配对展示 | **已实现**：按实际配对画成簇，节点带所在窝与学院标记 | `HomePairDiagram.tsx` |
| 蛋的性格 / 声音 / 性别 | 蛋条目里都没解出；性格与声音由父母推算；性别不标注 | `core.js` 蛋条目字段 |
| 巡查接口能否给父母 | **能**：`scene-info` 返回 `breeding_pairs` 与蛋的父母候选；属性仍按父母算 | 8.8 实测 |
| 巡查接口的蛋重 | **没有**：家园蛋无蛋重字段，满重只能给概率 | 8.8 实测 |

### 1.4 可复用资产

需求表、归档表、计划表、`plan_offers`、产线、旧详情页推荐配对算法；**家园配对展示**（`buildHomePairClusters` + `NestLayoutSvg`，已能把「谁配谁、各在哪个窝」画出来）。

## 2. 为什么不做货币

蛋神的崩盘路径：积分滥发贬值 → 出问题不回应 → 解散社群 → 会员与普通用户对立。

**【判定】** 可流通代币必然被增发与套利，运营方无法长期承诺兑换比例；一旦失衡，信任不可逆。保留市场形态，结算只用实物。

## 3. 目标与非目标

### 目标

- 组内成员同时表达「我要」与「我出」，撮合多对多、成交一对一。
- 归属自动匹配：平台两边的数据对齐，尽量不让用户手动指认。
- 两级标注：系统确认的可信、用户标注的可改，交换时双方都看得见来源。
- 现货优先，没有现货才退定制，并诚实提示等待时长。
- 把配对方案、批量发需求、搜索与筛选搬回来。
- 新手第一次进来只看到「现在能做的一小步」。
- 旧需求中心改造后融入，可退回。

### 非目标

- 不做积分、货币、代币、汇率、信誉分、等级。
- 不做跨组撮合、不做公开市场。
- 不做三方环形撮合。
- 不做自动成交；成交都需双方确认。
- 不做同蛋组通配。
- 不做赞助入口与会员体系。
- 不改造「共同寻找」任务体系。
- 不承诺挡位参与自动排序。

## 4. 核心模型

### 4.1 两层分离

| 层 | 关系 | 含义 |
| --- | --- | --- |
| 撮合层 | 多对多 | 一条「我要」列出多个可出候选；一条供给可被多条「我要」看到 |
| 成交层 | 一对一 | 一次确认锁定一笔；需求可累计多笔，直到数量满足 |

### 4.2 数量与接受式

- 每条「我要」带 `qty`（默认 1，上限 99）。
- 供给方发起**报价**，需求方**接受**才成立；不设抢单锁。
- 每接受一笔 `fulfilled + 1`；`fulfilled == qty` 时需求自动关闭并归档。
- 同一颗现货蛋只能挂在一笔进行中的成交上（库存级互斥）。

### 4.3 双路径结算

| 路径 | 触发 | 交付方式 | 是否需要上窝 |
| --- | --- | --- | --- |
| 现货 | 蛋仓里有符合条件、且已发布到组内的蛋 | 直接交接 | **不需要** |
| 定制 | 没有现货，或条件需现孵 | 一方孵、另一方等 | 需要 |

**【判定】** 现货不需要上窝：交易对象从「生产能力」变成「已存在的蛋」，交付是转移。

等待时长：定制必须给粗区间（1~2 天 / 3~5 天 / 需要现孵），注明估算；无产线数据不显示区间。

### 4.4 交付

交接卡：带什么（蛋 + 性格 + 奖牌）、去哪、几点、谁先给、联系人。

**绿窝单必须写明「哪只进绿窝」**：绿窝的位置就是性格选择，只写这对亲本不算完整交接。没有交接信息的成交不算闭环。

## 7. 归属：自动匹配 + 分配页

### 7.1 前提

订单是平台概念，家园是游戏数据，两边都在平台手里。**先自动匹配，匹配不了才让用户指认。**

### 7.2 输入

- 进行中的单：母本实例、种公实例、蛋物种、性格、数量。
- 家园快照：住户（实例、所在窝）、实际配对簇、窝（类型 / 房间）、地上的蛋（所在窝）。

### 7.3 匹配规则

1. 单的母本、种公实例 → 在家园住户里找到两只。
2. 两只落在同一个配对簇（母是 `femaleActorId`、公在 `maleActorIds` 里）→ 命中。
3. 命中的簇 → 占用窝 = 母窝 + 公窝；学院窝单独标。
4. 这些窝里有蛋 → 记「有蛋」，并带上快照时间。
5. 一个簇同时被多单命中 → 不猜，进分配页。
6. 换过亲本、换过窝、增量包缺失、实例对不上 → 不猜，进分配页。

### 7.4 输出

```
Binding {
  tradeId
  pairKey            // 母 actorId + 公 actorId
  nestKeys[]         // 该簇占用的窝
  hasEgg: boolean
  capturedAt
  boundBy: 'system' | 'user'
}
```

### 7.5 分配页（P11）

- 左列：未归属的配对簇 / 有蛋的窝；右列：进行中的单。
- 点选一次绑定；支持「这一簇全部归给这一单」。
- 绑定后写 `egg_trade_bindings`，`bound_by = 'user'`。
- 自动匹配命中的也写一条 `bound_by = 'system'`，用户可以在分配页改。
- 分配页只在有歧义时出现，不打扰正常流程。

### 7.6 与状态机的关系

**【判定】** 归属命中 + 窝里有蛋，界面显示「系统识别到已放窝」，但**不自动推进状态**（口径 13）：状态推进仍由一方点一次确认。自动匹配解决的是「是哪一单」，不是「替用户承诺」。

### 7.7 现货 ≠ 已在窝里（收紧保留）

- 蛋仓里的蛋 = 背包 / 蛋仓库里的蛋，可用于现货。
- 家园窝里的蛋 = 已经放进去的蛋，用于判定进度，不自动变成现货。
- 两者数据源不同，不能互相顶替。

## 8. 标注体系（两级来源）

### 8.1 内容（两边一致）

| 项 | 取值 | 说明 |
| --- | --- | --- |
| 体型奖牌 | 大块头 / 小不点 / 空 | 蛋重与体型等价，由蛋重判定 |
| 声音奖牌 | 婉转声 / 粗嗓门 / 空 | 由父母分贝平均推算，或用户标 |
| 性格 | 具体性格 + 概率 | 普通窝按父母计算；绿窝 = 学院那只的性格，100% |

不写精确体重；不写精确分贝；**不写性别**。

### 8.2 两级来源

| 来源 | 谁产生 | 界面标记 | 可否伪造 | 批量 |
| --- | --- | --- | --- | --- |
| 系统 | 采集 / 巡检自动标注 | 「系统确认」 | 不能（服务端写入） | 自动 |
| 用户 | 用户手动标注 | 无标记 | 可能记错 | 支持同物种批量 |

- 采集能自动标注的前提：蛋在家园里、能读到父母。
- 用户自己的蛋没有父母数据时，只给「用户标注」，不打系统标记。
- 交换时，交接卡与蛋卡都显示来源标记，双方都看得到。

### 8.3 性格概率

| 场景 | 概率 | 依据 |
| --- | --- | --- |
| 绿窝 | 100% | **学院小窝里那只自己的性格**；父母性格不同也不失效、不随机二选一 |
| 普通窝、双亲同性格 | 60% | 父 30% + 母 30% |
| 普通窝、单方目标性格 | 30% | 单方遗传 |
| 无父母数据 | 不显示概率 | — |

### 8.4 批量标注

- 入口：蛋仓 → 选一个物种 → 「批量标注」→ 设定奖牌 / 性格 → 应用到该物种下所有 `label_source = manual` 的蛋。
- 不覆盖 `system` 标注；要改只能逐颗改，且改完降级为 `manual`。

| 项 | 规则 | 出处 |

| 满重 | 蛋重 **等于极限值** 才叫满重；是概率事件，不是遗传属性，父母满重不保证后代满重 | `docs/domain/数据字段说明.md` L82 |

### 8.6 配窝示例（定版）

组合：**公 柴渣虫 · 固执 · 大块头 · 满重 · 96dB**（放在绿窝）＋ **母 菊花梨 · 保守 · 大块头 · 100dB**（普通窝）。

| 项 | 结果 | 原因 |
| --- | --- | --- |
| 物种 | **菊花梨** | 物种随母方 |
| 性格 | **固执** | 绿窝 100% 传学院那只（公本）的性格 |
| 体型 | **大块头** | 双亲都大块头 |
| 满重 | **不保证**，约 1/18 | 菊花梨蛋重区间 1.47~2.32，大块头阈值 2.303，满重 = 恰好 2.32，档内共 18 个取值 |
| 分贝 | **98dB，婉转声，非满分** | (96+100)/2 = 98，向零取整仍为 98；98 的绝对值 ≥ 96 有奖牌，但不满 ±100 |
| 性别 | **不标注** | 用户拿蛋时已知性别随机，写出来等于重复常识、白占位置 |

两条必须标注的前提：

- 1/18 的分母建立在「档内等概率」上，**这是用户口径，仓库文档没有记载**。
- 绿窝位置换人结果就变：若把母本（保守）放进绿窝，子代性格会变成保守。所以交接卡必须写「哪只进绿窝」。

### 8.7 蛋仓自动标注范围（定版）

按数据来源分两种，结果不同：

| 字段 | 背包蛋仓（本地采集） | 家园窝里的蛋（巡查接口） |
| --- | --- | --- |
| 物种 | 能（蛋条目宠物配置号） | 能（`npc_cfg_id`）；也可取母本物种 |
| 蛋重 | 能（`weightGrams`） | **不能**（家园蛋无蛋重字段） |
| 大块头 / 小不点 | 能（由蛋重判定） | 能（双亲都大块头 → 必然大块头） |
| 满重 / 非满重 | 能（比对区间端点） | **只给概率**，不标确定值 |
| 性格 | 能（按父母算） | 能（按父母算，规则见 8.3） |
| 声音 | 能（父母均值） | 能（父母均值） |
| 性别 | **不标注、不作为条件** | **不标注、不作为条件** |
| 精确体重 | **不给** | **不给** |
| 归属哪一单 | 能 | 能（自动匹配；多单命中进分配页） |

结论：**家园蛋唯一算不出的是「满重 / 最小体重」这一档**，因为它需要蛋重值；性格、声音、体型都可以由父母算，不依赖接口的 `genetics` 字段。
用户把蛋收进背包后，满重自动从「约 1/N」升级为确定值。

### 8.8 巡查接口能力（实测，2026-11-16）

实测方式：`POST /api/v1/games/rocom/ingame/home/scene-info`，body `{"uid": <游戏UID>}`，账号 293143。

**返回结构（只列与本方案相关的）**

| 字段 | 内容 |
| --- | --- |
| `breeding_pairs[]` | 配对列表；每对 = `female`（actor_id、`furniture_guid`、`nature`、`voice`、`pet_cfg_id`、名字）+ `male_partners[]`（每个公本同样带窝与属性） |
| `eggs[]` | 每颗蛋 = `npc_cfg_id`、`nest_furniture_guid`、`mother_candidate`、`father_candidates[]`、`parentage_status`、`biological_parentage_confirmed`、`genetics` |
| `egg_parentage` | `{ biological_parentage_confirmed, reason, status }` |
| `snapshot_status` | 快照有效性 |

**关键结论**

1. **配对不是缺项。** 6 对配对完整返回，公本可多个（对应学院 1:2）。蛋上直接带 `mother_candidate` 与 `father_candidates[]`，本次样本 `parentage_status = unique_current_pair_candidate`，与 `breeding_pairs` 中的一对完全对上。
2. **父母是「当前候选」，不是「历史确认」。** 样本 `biological_parentage_confirmed = false`，`reason` 原文：*current pairing candidates are available, but historical biological parents cannot be confirmed*。蛋是历史上孵的，期间配对可能变过，游戏只能担保当前候选。
3. **`genetics.status = "unavailable"` 不影响作业。** 它只是游戏侧的基因预览未开放；性格、声音、体型一律按 8.5 的规则用父母算。
4. **窝 GUID 有精度差。** 同一只精灵的窝在不同字段里低位被截断，例如蛋的窝 `…142143`、母候选的窝 `…142000`。**禁止字符串全等比较**，要用 `furniture_guid_exact`，或按高位前缀 / 数值容差匹配。不做这一步，归属自动匹配会全部落空。

**展示口径（定版）**

| 情形 | 界面表述 |
| --- | --- |
| `parentage_status = unique_current_pair_candidate` | 「当前配对：X × Y（游戏未确认）」 |
| `biological_parentage_confirmed = true` | 直接显示父母 |
| 父母缺失 / 候选冲突 | 「父母暂无记录」 |
| 家园蛋的满重 | 「约 1/N」，不标确定值 |

**成本**：`scene-info` 与 `home/info`、`home/eggs` 各计 1 次调用；同一次巡查若要窝、蛋、配对三样，需 2~3 次调用，配额护栏按调用次数计。

## 10. 撮合算法

### 10.1 输入

```
MatchInput {
  groupId, viewerAccountId
  wants: DemandKey[]        // 蛋 + 性格 + 体型 + 声音 + 满重档 + qty + fulfilled（不含性别）
  supplies: SupplyItem[]    // 蛋 + 性格 + 概率 + 奖牌 + stockId? + 来源 + 新鲜度 + 绿窝可用（不标性别）
}
```

### 10.2 输出

```
MatchResult {
  demandKey
  candidates: [{
    supplyId, ownerAccountId, matchType,
    natureLevel: 'exact' | 'probable' | 'unknown',
    natureProb, freshness, greenNestOk,
    waitHint, reasons[], labelSource
  }]
  excluded: [{ supplyId, reason }]
}
```

### 10.3 匹配层级

1. 性格：供给性格 == 需求性格且概率 100% → 精确；概率 >0 → 可能；未知 → 只能定制。
2. 体型 / 声音：奖牌满足即通过；需求为精确值（如 +100）而供给只有奖牌 → 标「可能」，不判精确。
3. 性别：需求与供给都不含性别条件，撮合不因性别筛选，概率计算里也不出现性别因子。
4. 绿窝：需求要求时必须可绿窝且当前未占用。
5. 现货优先于定制；同层按新鲜度、来源、更新时间排序。
6. 挡位只标注，不参与排序。

### 10.4 纯函数

输入输出确定，时间与占比作为参数传入；先按蛋分桶再匹配，组内量级可控。
