## 一、结论

**需先修（不可直接提交）。**

- 有一处**违反明确业务口径**的状态机漏洞：学院第 2 条配对方可能已经被普通 30% 配对占用，导致「学院簇不再干净、学院配对方又去配别的异性」——这正是口径③「宁可牺牲也不弄错」禁止的情况。已给出 4 只精灵的最小确定复现。
- 有一处**输出错误**：`gender: '未知'` 的精灵会被选为「学院那只」，占掉唯一的绿窝却产不出任何 pairing，同时 `slots` 把它显示成「母」、`unfilled` 谎报已覆盖（已复现，且解析器确实会产出 `未知`）。
- 有一处**记账与结果不一致**：`unfilled` 由候选级 `filledCells` 推出，而实际连线由几何 `targetOf` 推出，二者粒度不同，会出现「`unfilled` 为空但某缺口根本没有配对」。已复现（约 15% 的随机小场景命中）。
- 重点审查项①（`GROUP_GAP` 组间距离）**未发现反例**：穷举组规模 1..11 的两两/三组组合，跨组最小中心距恒为 6 > 4.25 格（见 §四.1）。但组内「紧凑块」在规模 ≥5 时并不两两相连（已知、非 bug，见 §三）。

## 二、阻塞级问题

### B1. 学院第 2 条配对方可被普通 30% 配对占用（脏学院簇）——违反口径③

**位置**：`src/domain/nestPlan.ts` L277–L291（分配主流程）、L246–L275（`tryAccept`）。

**成因**：
```ts
for (const candidate of normal60List) tryAccept(candidate, false);
for (const candidate of accepted) { usedByNormal.add(candidate.p1); usedByNormal.add(candidate.p2); } // ← 只把 normal60 写进 usedByNormal
for (const candidate of academyList) tryAccept(candidate, false);        // 学院第 1 条
for (const candidate of normal30List) tryAccept(candidate, false);       // ← normal30 的精灵从未写入 usedByNormal
for (const candidate of academyList) { ... tryAccept(candidate, true); } // ← 学院第 2 条：这里检查 usedByNormal 已失效
```
`usedByNormal` 只统计了 normal60 的占用；normal30 在学院第 2 条之前就已被接受，但它的精灵没有补进 `usedByNormal`，于是第二遍学院 pass 会把「已属于某条普通 30% 配对」的精灵再挑成配对方。`costOf` 按「是否已 placed」计费，所以窝数不会算错，但**同一只精灵同时出现在学院档和普通档两条 pairing 里**，且组件并查集会把两条配对并进学院簇（`componentOf` L294–L329），学院簇因此不再「单独成组」。

**最小复现（4 只精灵，单账号）**：
```ts
// species: 801 甲兽 eggGroups [2]
const acad = mk(801, '母', '认真');   // 学院那只（带目标性格“认真”）
const k    = mk(801, '公', '胆小');
const f    = mk(801, '母', '固执');
const q    = mk(801, '公', '胆小');
buildNestPlans({ species, owned: [acad, k, f, q],
  coverage: coverage(cell(2,'认真'), cell(2,'固执')), mode: 'perfect' });
// 覆盖 0 个普通 60%（固执/认真都没有“同性格异性对”）
```
**实测输出（复现成功）**：
- `clusters` = **只剩 1 个组**，4 个窝挤成 2×2：`[[(0,0),(2,0),(0,2),(2,2)]]`（学院簇被并入普通配对）。
- `pairings` = 2 条 `academy`（固执）+ 2 条 `normal30`（认真）：`[["academy","固执",...],["academy","固执",...],["normal30","认真",...],["normal30","认真",...]]`。
- **学院配对方（`k`/`q`）同时出现在正常配对里** → 违反口径③。

随机小场景搜索（5000 例）中该形态出现 61 次，非孤例。

**修复建议（任选其一）**：
1. 在 normal30 pass 结束后、学院第二遍 pass 之前，把**非学院**的 accepted 精灵补进 `usedByNormal`：
   ```ts
   for (const c of accepted) if (c.tier !== 'academy') { usedByNormal.add(c.p1); usedByNormal.add(c.p2); }
   ```
   （注意不要无脑遍历 `accepted`，否则会把 `academyPet` 自身也加进去，导致第二遍学院候选全被误拒。）
2. 或把「学院第二遍」提到 normal30 之前（但那会改变 60→学院→30 的优先级语义，需业务确认）。
3. 或在 `tryAccept` 的学院分支里加一条：若配对方（`p1===academy ? p2 : p1`）已被 `placed` 且不在 `reserved` 中，则拒绝。

**回归断言建议**：修复后，学院档 pairing 的精灵集合与普通档 pairing 的精灵集合必须**交集为空**；本用例 `clusters.length === 2`、学院簇大小 `=== 1 + 配对数`。

### B2. `gender: '未知'` 可被选为「学院那只」，产出为零且输出性别被篡改

**位置**：`src/domain/nestPlan.ts` L174–L182（学院候选生成），L136（`toNestPet`），L385（几何连线跳过未知性别）。

**成因**：
- 学院候选的 `academy` 来自 `carriers`（只按性格+档位筛，**不查性别**）；内层只检查 `partner.gender === '未知'` 与 `partner.gender === academy.gender`。当 `academy.gender === '未知'` 时，`'公' !== '未知'` 成立，于是**未知性别的携带者会被推成学院候选**（`mother` 落到了 partner 身上，绕过了本意）。
- `tryAccept` 不查性别 → `academyPet` 被锁定为这只未知性别精灵，绿窝被占死。
- 几何连线 `if (A.pet.gender === '未知' || B.pet.gender === '未知') continue;`（L385）→ 该窝**一条 pairing 都产不出**。
- `toNestPet`（L136）`gender: pet.gender === '公' ? '公' : '母'` 把「未知」**静默显示成「母」**。
- `tryAccept` 已 `markFilled`，所以 `unfilled` 会谎报该缺口「已覆盖」。

**可达性**：`parseBackup.ts` 的 `normalizeGender` 在字段缺失/无法识别时返回 `'未知'`（L104–105），因此真实数据里会出现未知性别精灵。

**最小复现（2 只精灵、1 个缺口）**：
```ts
const u = mk(801, '未知', '固执'); // 甲兽[2]，未知性别、带目标性格
const m = mk(801, '母', '认真');
buildNestPlans({ species, owned: [u, m], coverage: coverage(cell(2,'固执')), mode: 'perfect' });
```
**实测输出**：`pairings = 0`；`unfilled = []`；`slots = [{gender:'母', nature:'固执', academy:true}, {gender:'母', nature:'认真', academy:false}]`、`nestsUsed = 2`。
即：唯一的绿窝被一只未知性别精灵占掉、性别还被显示成「母」、缺口却被标为已覆盖。

**修复建议**：
1. 学院候选生成时排除未知性别：`if (academy.gender === '未知') continue;`；（`carriers` 里过滤，或在内层对 `academy.gender` 显式校验）。
2. `toNestPet` 不要无条件把非公当母：未知就保留 `'未知'`（同时把 `NestPet.gender` 类型放宽为 `'公' | '母' | '未知'`），至少不能把未知渲染成母。
3. 兜底：`unfilled` 不应相信候选级的 `markFilled`（见 B3）。

### B3. `unfilled` 与实际配对不一致（候选级记账 vs 链路级结果）

**位置**：`addsNewGap`/`markFilled`（L234–L245、L266）、`unfilled`（L430–L432） vs `targetOf`（L353–L376，尤其 L369 `const natureName = [...hit.keys()][0];`）。

**成因**：接受候选时按**候选**（可跨多个组/性格）把缺口标为已覆盖；但最终产物是**几何连线**，`targetOf` 对一条连线只返回一个 `natureName`（`hit.keys()[0]` 任取）。当一条精灵对同时是「两个不同性格候选」的载体（典型：母方物种有两个可孵蛋组，或双方各带不同目标性格），两个缺口都会被 `markFilled`，但同一条连线只能归到一个性格 → 另一个缺口**没有任何 pairing 覆盖，却不在 `unfilled` 里**。

**最小复现（5 只精灵）**：
- 物种：801 甲兽[2]、802 乙兽[7]、803 丙兽[2,7]；全部「大婉」。
- `owned`：`802/公/认真`、`803/公/胆小`、`803/母/认真`、`801/公/莽撞`、`802/公/胆小`。
- `coverage`：`(2, 认真, 大婉)`、`(2, 胆小, 大婉)`。

**实测输出**：`pairings = [normal60 认真, normal30 认真]`，`unfilled = []`，但**没有任何 pairing 覆盖 `(2, 胆小)`**；`slots` 只放了 3 只。即：提示「缺口已补齐」，实际没产出。

随机小场景搜索中该不一致在 5000 例里命中 745 次（≈15%），非常容易踩到。

**根因延伸**：即便忽略 `unfilled`，`targetOf` 用 `[...hit.keys()][0]` 在多个命中性格里**任取一个**也是不确定语义（受 `cells` 顺序影响）。

**修复建议（择一）**：
1. `unfilled` 改由**几何结果**推导：遍历 `pairings` 累加被覆盖的 `(grade, natureName, groupId)`，再与目标缺口求差；彻底不依赖 `filledCells`。
2. 或在 `markFilled` 时只标记「这条候选在几何上确实能产出的那一个缺口」，与 `targetOf` 用同一套判定（把两者合成一个函数）。
3. 明确多性格命中的业务语义（一条边只产一颗蛋 → 只应覆盖一个性格），并据此重构。

## 三、非阻塞建议

1. **注释与实现不符（认知风险）**：`nestPlan.ts` 顶部「同一条连通组内的精灵都是目标相容的（组内任意公母配对都是我们要的蛋）」**不成立**。组件的并查集按「共享精灵」合并（L294–L329），会把不相容的异性并进同一簇 → 产出 `blockedLinks`。随机搜索里确实出现非空 `blockedLinks`（且多数与 B1 的脏簇同源）。建议改写注释，或让组件并查集按「目标相容」建边。
2. **`isolation` 字段名名不副实**（审查项⑦）：现在返回的是「编组式布局校验」（跨组串线 + 重叠），不再是「隔离式」。建议改名 `layout` / `layoutReport`；`LayoutReport.ok` 的语义与注释同步。
3. **`NestPairing.academyParent` 契约不符**：接口注释写「普通档为 null」，但 L416 无条件 `academyPet ? toNestPet(academyPet) : null`，普通档在该账号有学院精灵时也会拿到非 null。要么改注释，要么普通档置 null。`partner` 字段注释同理（普通档 = 两只中的第二只，实测如此，OK）。
4. **`academyList` 预过滤过严（疑似）**：`candidate.groupIds.every(g => !has60.has(...))` 会把「G1 无 60、G2 有 60」的学院候选整条丢弃，丢掉它对 G1 的 100% 价值。口径⑥只说要接「凑不出 60%」的缺口，未明确多组候选如何处理，建议按组拆分。
5. **排序度量不一致**：`byGroupsThenStable` 用 `groupIds.length` 排序，接受判据却用 `addsNewGap`（新缺口数），局部会先被「组数多但零新缺口」的候选占位。建议排序改用「新缺口数」。
6. **未用导出**：`nestPlan.ts` 末尾 `export { PAIR_RANGE }` 目前无人从这里 import（测试都从 `nestGeometry` 取），疑似转发死代码。`GROUP_GAP` 仅在被测模块内部使用，导出可留可删。
7. **重复计算**：每个 `cell` 内都重算 `accountOwned.filter(classifyGrade...)`（L160）；`cells` 通常很小，影响可忽略，可提到 cell 循环外缓存。
8. **健壮性**：`nestCount` 为负/非整数无校验（`nestsUsed = nestCount - nestsLeft`）；`nestCount < 2` 时行为正确但没有任何提示。

## 四、重点审查项逐条结论

1. **布局正确性（组间距）**：**未发现反例，正确**。`componentOffsets` 让每组 x 从 0 到 `(cols-1)*2`，`cursor += width + GROUP_GAP`，故任意相邻两组的**最小水平间距恒为 `GROUP_GAP = 6` > 4.25**，与组规模无关。穷举 size 1..11 的两两组合、以及三组组合，跨组最小中心距实测 `minCross = 6`，`checkLayout().ok` 全为 `true`。（附带：单组 size≥5 时组内不再两两相连，例如 size=5 的 `(4,0)-(0,2)` 距离 4.47、size=11 的最大距离 7.21，都 >4.25——这是"紧凑块"的固有性质，只减少连线、不产生错误蛋，非 bug。）
2. **`tryAccept` 四状态自洽性**：`reserved` 有效阻止普通配对复用学院精灵；`academyPet` 锁保证只会有一只学院精灵（未发现"两只学院"）。**漏洞在 B1**：`usedByNormal` 在 normal30 之后未刷新。
3. **`targetOf` / `natureChanceFor` / `gradeOf`**：`gradeOf` 用 `classifyGrade`，两侧档位不一致会被 `grade !== gradeOf(father)` 挡掉，正确；`natureChanceFor` 的学院分支按「学院那只自己的性格」判定，与口径⑤一致。**漏洞在 B3**（多性格命中时 `hit.keys()[0]` 任取）。
4. **边界**：空 `owned` → `plans = []`，不抛；全 `covered` → 无候选，`unfilled` 为空；`nestCount < 2` → 无配对、`nestsUsed = 0`，不抛；`nestCount` 很大 → 布局正常、`isolation.ok`；**`gender:'未知'` 见 B2（有 bug）**；两只内容完全相同的不同对象按对象身份处理（正确，会各占一个窝）。未发现 NaN 或死循环。
5. **复杂度**：`O(账号数 × 缺口数 × 每账号宠数²)`。按账号切分后宠数通常可控，最坏量级可接受；无明显重复计算热点（`graded` 可缓存，收益小）。
6. **测试覆盖缺口**：见 §五。
7. **可维护性**：见 §三 1–3。

## 五、缺失的边界测试清单

（用例名 + 断言要点；其中带 ★ 的为能直接抓到本次 B1/B2/B3 的回归测试）

**`nestGeometry.test.ts`**

1. `跨组任意规模都不串线（穷举）`：对 `sizes = 1..11` 的两两组合（可加三组），断言 `checkLayout(buildGroupedLayout(sizes)).ok === true`，且跨组任意两窝 `nestsConnect === false`、`centerDistance > PAIR_RANGE`。（现有测试只覆盖 `[4,2]`。）
2. `单组规模 1..11 无重叠`：`checkLayout([buildGroupedLayout([k])[0]]).ok === true`。
3. `大组允许组内不完全连通（记录已知事实）`：`buildGroupedLayout([5])` 中 `(4,0)-(0,2)` 距离 `≈4.47 > 4.25`；`buildGroupedLayout([11])` 最大组内距离 `≈7.21`。防止后人误以为"组内全连通"。
4. `空输入与单窝`：`buildGroupedLayout([]) === []`；`buildGroupedLayout([1]) === [[{x:0,y:0}]]`。
5. `GROUP_GAP 契约`：`GROUP_GAP > PAIR_RANGE`（值 6）。

**`nestPlan.test.ts`**

6. ★ `学院第 2 只配对方不得已被普通 30% 占用`：用 §二.B1 的 4 只精灵；断言学院档 pairing 的精灵集合 ∩ 普通档 pairing 的精灵集合 = ∅；`clusters.length === 2`（学院簇与普通簇分开）；学院簇内不存在普通档 pairing。
7. ★ `未知性别不得成为学院那只`：用 §二.B2 的 2 只精灵；断言 `pairings`（或 `slots`）里不存在 `academy === true` 且原始性别为「未知」的窝；`unfilled` 必须包含该缺口（不能被谎报覆盖）。
8. ★ `unfilled 与 pairings 自洽`：对每个 `coverage.cells` 中 `state !== 'covered'` 的缺口，若不在 `unfilled` 中，则 `pairings` 里必须存在 `grade`+`natureName`+`groupIds.includes(groupId)` 匹配的一条。用 §二.B3 的 5 只精灵做固定用例。
9. `学院巢唯一 + 最多 2 条线`：构造两个不同性格的学院携带者 → 断言 `slots.filter(s => s.academy).length === 1`，学院档 pairing 数 `<= MAX_ACADEMY_PARTNERS`，且 `academyPet.name/nature` 只有一种。
10. `窝数不足的降级顺序`：`nestCount` 从小到大的多组断言——先保 normal60、再学院、再 normal30；`nestsUsed <= nestsTotal`；超出的缺口进 `unfilled`（现有测试只覆盖 `nestCount=2` 的一种）。
11. `nestCount < 2`：`nestCount = 0 / 1` → `pairings = []`、`nestsUsed = 0`、不抛。
12. `空背包 / 全 covered`：`owned = []` → `plans = []`；`cells` 全 `covered` → 该账号无候选、`unfilled = []`、不抛。
13. `nestCount 很大`：`nestCount = 50` → 不抛、`isolation.ok === true`、`clusters.length === 实际连通组数`（不随窝数增大而变）。
14. `同账号两只内容完全相同的不同对象`：两只完全相同（同 gameId/gender/nature/档位）但**不同对象**的精灵 → 断言各自占一个窝（`nestsUsed === 2`、`slots.length === 2`），不会因内容相同被合并。
15. `academyParent 字段契约`：普通档 pairing 的 `academyParent` 期望值（按现状为非 null；若按接口注释应为 null，则明确写死一种并改实现/注释）。
16. `slots 性别保真`：`slots` 中每只 `pet.gender` 与输入原始性别一致（尤其未知不得变母）。
17. `跨组不串线（端到端）`：遍历 `slots`，断言不同 `cluster` 的两窝 `nestsConnect === false`（现有测试只断言 `isolation.ok`）。
