# 全站页面职责与导航评审

日期：2026-10-24。基于当前源码与两份母本共享规格，只读产品评审；未访问真实账号，未修改产品代码、Git 或部署。以下体验判断是依据界面结构提出的风险与建议，不是用户研究结论。根任务正在处理的“组长”“未收集”与已入组时表单下移视为既定约束。

建议采用分阶段的四入口结构：**首页 / 收集 / 小组 / 我的**。首页回答“目前怎样、下一步做什么”，收集回答“我的目标还缺什么、怎样补”，小组回答“如何借助组员一起补”，我的回答“身份和数据是否可用”。种公覆盖、配窝与求蛋保留为收集中的完整工具；不是缩成只服务母本的产品。精灵库存保留独立详情路由，可从收集进入。

## 2. 九项有证据的发现

### F1：看板成为多个完整工具的容器，进度与行动难以形成主次（高）

证据：目标设置在 `Dashboard.tsx:172`，母本档位明细在 `:246`，推荐在 `:326`，完整 `NestPlanCard` 在 `:357`。母本库存能力又在 `MotherView.tsx:434` 提供。风险不是简单“页面太长”，而是用户进入首页前需判断设置、查已有、配窝三个不同任务。建议首页保留进度、最新变化、最多少量可直接执行的下一步；详细母本列表和全部配窝移至收集，但通过直达链接保留熟手速度。

### F2：“我的精灵”包含库存和未拥有目标，种公/母本同级却含义不同（高）

证据：种公集合是 `describeStudTargets(...).filter(hit => hit.grade !== null)`（`MyPets.tsx:143`）；母本集合则以图鉴蛋为全集，包含完全未拥有的目标（`:133`），默认显示未收集（`MotherView.tsx:206`）。看板种公卡“看我的种公”跳库存，母本卡“看我的待补齐母本”跳目标（`Dashboard.tsx:226`、`:235`；`App.tsx:159`）。建议“收集·种公/母本”统一以目标为主，已有个体作为展开明细；精灵库仍专门查自己有哪些个体。种公“未达目标”与“没有合格公”应继续区分，不能把有用的非目标性格公藏掉。

### F3：目标定义被命名为筛选，且分散在不同页面（高）

证据：`coverageFilterStore.ts:14` 明确这些“筛选”决定看板/覆盖度/换什么分母；档位在首页改（`Dashboard.tsx:199`），蛋组与性格在覆盖度改（`Coverage.tsx:93`、`:99`），母本达标在母本改（`MotherView.tsx:363`）。普通种公库存筛选又是另一套（`MyPets.tsx:164`）。建议概念分三层：**游戏账号范围 / 收集目标 / 当前列表筛选**。先统一可见摘要和编辑入口，保持原值与算法；以后再拆持久化类型。暂不要把所有控件物理塞进“我的”，否则查看目标时还要跨页编辑。

### F4：同名“母本全收集”下面的档位明细与卡片并非同一个查询（中）

证据：进度用 `countQualifiedMotherChains` 与个人 `MotherCriteria`（`Dashboard.tsx:88`）；下方明细按每颗蛋的 `motherClass === motherGrade` 过滤（`:78`），而且只挑一个代表个体（`:97`）；标题仍是“母本全收集”（`:251`）。这不是已证实的统计计算错误，但会造成“卡片已收集数”和“这个档位数量”之间的理解冲突。建议主进度只用个人收集条件；档位视图保留在精灵库/收集的高级查看里，标“按代表档位查看”，不要暗示它就是该条件所有持有个体。

### F5：母本协作藏在种公求蛋入口，业务对象不连续（高）

证据：`Swap.tsx:24` 定义的是种公目标求蛋清单，`:85` 又加入母本共享主分段；小组不要求本地数据也可进入（`MotherSharing.tsx:23`），而种公求蛋要求导入（`Swap.tsx:125`）。建议小组独立主入口，母本缺口行可“去小组找”；种公求蛋仍归个人收集。小组入口可达不应绑定本地精灵库存是否为空。

### F6：已有确定的导航落点风险，重构必须首先解决“去哪里”的合同（高）

证据：推荐“全部”调用 `onOpenSwap`（`SuggestionCard.tsx:69`），App 只 `setTab('swap')`（`App.tsx:167`）；Swap 恢复持久化的 `eggs/sharing`（`Swap.tsx:87`）。因此上次停在共享后，点种公推荐全部可能回到共享而非求蛋。这是源码可确定的路径风险，本报告未浏览器复现。类似问题不应靠清空所有记忆解决；需类型化导航意图，如“打开种公求蛋”“打开某蛋组迭代”“打开母本未收集”，同时保留用户手动切页时的上次位置。现有蛋组展开聚焦已经示范了正确意图（`App.tsx:168`）。

### F7：“导入数据”已经是身份与数据中心，命名无法覆盖实际目的（高）

证据：登录共享入口通过 `onGoAccount`，App 将其跳到 import（`App.tsx:193`）；里面实际有云身份、恢复码和注销（`AccountPanel.tsx:22`、`:282`），并承载私有数据维护（`ImportPanel.tsx:518`、`:526`）。建议改“我的”，内部按“工具箱身份 / 游戏账号与导入 / 私有云同步 / 更多数据操作”组织。恢复码用于同一工具箱身份，不是新增游戏号；“我的”不能再等同“我的精灵”。

### F8：个人缺口、小组缺口与资源目录的事实来源不同，不能为统一导航而合并模型（高）

证据：个人统计来自筛选后的本地快照（`useOwnedPets.ts:23`），个人默认母本条件是大小体型与±100（`domain/motherCriteria.ts:25`）；组摘要固定母+大块头+100（`domain/motherResource.ts:21`）。`domain/motherSharing.ts:118` 在自己不可比较时返回 null；`:137` 中 all 是全量目标，并非组缺口。建议显示范围与口径；“我未收集”不能直接等于“组里缺”。共同未收集只能由无人持有且没有未知成员的行推导；待发布/不兼容必须保留待确认。二期认领可以贴在共同缺口上，不能把现有 all 简单改标签当任务队列。

### F9：已有计划是意向，达成来自库存；未来认领还多一层责任，不能都用勾选完成（高）

证据：`motherPlanStore.ts:4` 注释明确达成不存，导入后实时判定；`MotherView.tsx:411` 提供个人计划。组资源覆盖同样由摘要派生（`domain/motherSharing.ts:48`）。建议可共用行动卡视觉与跳转，保持“个人想收 / 组内负责寻找 / 已持有”三种状态各自的数据归属。把配窝建议、求蛋候选或认领都直接计入收集进度会破坏“收集轻松”的信任基础。

## 3. 导航方案与代价

| 方案 | 顶层入口 | 收益 | 成本与限制 |
| --- | --- | --- | --- |
| A 最小调整 | 看板 / 我的精灵 / 覆盖度 / 换什么 / 我的 | 老用户迁移成本小；先让我的承接身份数据，并修确定落点 | 母本目标仍藏库存、小组仍藏种公入口；继续维护两套目标查看路径，不能根治职责问题。适合作为过渡 |
| B 目标导向四入口（建议） | 首页 / 收集 / 小组 / 我的 | 按个人目标、多人协作和数据维护分工；保留所有专家工具，移动端主导航更轻 | 需构建收集内路由、迁移旧入口和视图状态，必须明确种公工具的直达路径；不是一次改名即可 |
| C 独立补齐第五入口 | 首页 / 收集 / 补齐 / 小组 / 我的 | 高频在母本计划、配窝与求蛋间切换时，行动可常驻 | 收集与补齐切开后，同一缺口容易出现两份搜索/筛选/详情；补齐还要分个人母本计划、种公配窝/求蛋、小组认领，首次打开增加解释成本。若只放最近行动摘要，首页已承担此职；若放完整工具，收集又容易退化为静态成绩单 |

推荐 B，但先以 A 的低风险方式建立导航合同，再迁移 B。C 可作为后续选项：只有观察到用户经常管理跨目标的固定行动队列、需要在保留收集页上下文时高频切换执行，才值得增加第五入口；这需要验证，不能依据目前代码体量推出。即使届时增加，也应叫“补齐”，避免“计划”误把事实和意向混在一起，小组认领仍以小组为数据归属。

## 4. 推荐结构与实际访问深度

“一次操作”按点击导航或任务按钮计，不把滚动当路径层级；以下是建议验收目标，不是现状测量。

| 入口的一个主要任务 | 默认内容 | 完整能力与路径 |
| --- | --- | --- |
| 首页：决定下一步 | 当前账号范围与目标摘要、种公/母本进度、最新新增、少量有原因的下一步 | 首页点“自己孵”直接到种公配窝；“求蛋”直接到种公求蛋；“补母本”直接到母本未收集；“组员有”到对应组/蛋。均 1 次跳转，不能只切顶层后任由旧子视图覆盖 |
| 收集：核对和补齐个人目标 | 母本/种公两种目标，记住手动选择；每种都先显示目标进度与缺口 | 进入收集再选种公，最多 2 次看到种公缺口。种公同级任务视图为“覆盖矩阵 / 自己孵 / 求蛋”；不要做“收集→高级→工具→覆盖度”的深链。首页精准直达各视图；收集页再切一种任务最多 1 次。覆盖行展开详情与当前机制一致 |
| 小组：利用共享资源协作 | 当前组、组内状态、我缺的/我能补谁；二期再加共同未收集与认领 | 持有来源和成员详情按需展开；发布面板作为状态卡进入，避免每次找资源先穿过大表单。管理/创建/加入为次级操作；无本地数据也能浏览 |
| 我的：维护身份与数据 | 工具箱身份、私有同步状态、游戏账号数据新鲜度、导入主操作 | 恢复码/换设备/退出；导入历史、导出/合并/重置；游戏账号列表。原分享自动导入必须持续可用，不能因切页结构改动丢事件 |

收集中的**精灵库**作为次级路由提供全部个体、种公库存与所有细筛选；通过收集页固定“查看精灵库”入口（1 次）及目标行“查看已有”可达。这里不承载未拥有目标，也不放到“我的”身份页。顶层“收集”记忆上次母本/种公视图，不代表首页直达可以忽略目标。种公配窝允许完整查看、钉选与复制，专家能力下沉是收起默认复杂度，不是删算法或少给字段。

## 5. 功能去向矩阵

| 现有能力 | 去向与默认位置 | 保留/迁移原则 |
| --- | --- | --- |
| 导入新增 | 首页摘要；我的内历史与完整结果 | 两处可以是同一事实的摘要与详情，不要独立计算新增 |
| 个人模式、种公档位/蛋组/性格 | 收集目标摘要的“调整目标” | 首页也能打开同一编辑器；第一阶段继续读写原 store |
| 母本达标条件 | 收集·母本的“收集条件” | 不跟随列表筛选清空；与种公目标有区别，不强行同一份条件 |
| 母本已收集/未收集、个人计划 | 收集·母本 | 计划只是关注子集；进度仍由导入事实派生 |
| 种公覆盖矩阵与迭代详情 | 收集·种公·覆盖矩阵 | 默认显示缺口摘要，完整矩阵保持可达；首页可带蛋组聚焦 |
| 配窝建议、钉选、复制 | 收集·种公·自己孵 | 首页留少量摘要与精准入口；不删高级完整路线 |
| 优质种公推荐/完整求蛋清单 | 收集·种公·求蛋 | 首页推荐摘要与完整列表同用现有算法，无需两份推荐维护 |
| 全部个体/种公库存/背包位置/筛选 | 收集→精灵库；目标行展开已有 | 保留“合格公但不覆盖当前性格目标”的资源，不用目标筛掉库存 |
| 母本按档位明细 | 精灵库高级视角或收集已收集的次级查看 | 明确代表档位语义，与个人达标覆盖数量区分 |
| 共享发布、三资源视图、成员管理 | 独立小组入口 | 保留独立身份、选号、口径、发布预览、未知语义 |
| 共同未收集/寻找认领 | 小组二期，重构之后实施 | 在当前目录之外加派生任务视图；事实覆盖与认领独立 |
| 工具箱身份/恢复码/私有云同步 | 我的 | 不与组资源发布合为“同步”；本机导入后保持当前自动私有同步行为 |
| 导入/采集说明/历史/导出/合并/重置 | 我的 | 分享入口复用同一导入服务；低频破坏性维护留次级区 |
| 教程/数据来源/特殊性别知识 | 原入口保留，相关目标旁放上下文入口 | 不强制新手先读完整领域指南；未理解前仍能查进度和缺口 |

## 6. 安全架构边界与上线顺序

1. **先建立导航意图，后移动界面。** 让 `App` 接受目标页、母本/种公视图、任务视图、可选蛋组/蛋 ID；首页快捷入口明确指定目标。普通点主导航才恢复上次状态。保留旧 TabId 的兼容映射及 `lastTab` 读取，否则旧设备恢复会落到未知页。先验证 F6。
2. **冻结事实与口径计算，只改变组合。** 沿用 `computeStudCoverage`、`buildNestPlans`、`computeStudRecommendations`、`groupMothersByEgg` 与母本条件函数。可以提取共享查询 hook，避免页面自己拼不同口径；不能以“少代码”为由让私有/小组共用同一个过滤后的 owned。看板摘要与详情必须使用同一输入快照和条件。
3. **保留本地数据、设置与旧入口。** 首轮不改 `roco.*` 键与同步优先级。现有云端优先条件在 `src/api/sync.ts:20`、`:46`；将“目标”和“显示筛选”正式拆类型/迁移键应另批做，不能在导航重构里悄悄改变两台设备合并行为。旧入口先指向新具体视图并提示位置，回滚仍能读原设置。
4. **迁移首页与我的，再收集，最后独立小组。** 我的先组合已有导入与身份面板；首页只削减完整明细但保留直达。收集先组合旧母本页、覆盖度、配窝、求蛋和精灵库，不重写结果。小组抽离 Swap 后，保持 `useMotherGroups` 的会话/组切换清理与请求代数（`src/ui/useMotherGroups.ts:128`、`:155`）、可见时刷新（`:334`），不要把它提升为全站持续轮询。
5. **导入监听从页面生命周期解耦，或保持兼容容器。** 当前分享事件特意先切 import 才能挂载消费监听，完成再跳看板（`App.tsx:24`、`:63`）。将 import 改为“我的”的子路由时，要有全局接收/导入协调器或相同挂载保证；不是仅改导航 label。导入完成后先呈现新增，登录共享前往“我的”完成后允许回到原组/邀请码。
6. **再做小组二期。** 共同缺口、未知、认领与组统一口径单独领域/API迭代；不在导航迁移中改数据库或把认领塞进 `motherPlan`。按用户较新要求安排组口径，不能仅沿用旧讨论稿固定先后顺序。
