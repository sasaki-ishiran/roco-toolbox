# Android 采集器 1.2.6 源码初审

审查在产品修复及生产部署完成后进行。提供物为完整源码，未执行 APK、未启动游戏 VPN、未调用作者上传接口，也未复制源文件到产品。结论是静态源码可行性判断，不代表真机集成已经通过。

## 结论

可以让“洛克工具箱”安卓 APK 直接采集。现有 `android-shell` 已能托管产品页面及接收 PCAP，新增原生采集模块后即可形成“工具箱开始采集 → 系统 VPN 授权 → 打开游戏 → 停止并保存 → 本机解析导入”的闭环。浏览器/PWA 无法通过网页 API 获得 Android VpnService，需要另发包含原生模块的新 APK；网页部署本身不会给已安装旧 APK 增加采集能力。

更适合先复用采集和转发层、继续使用我们已经验证的本地 PCAP 解码器。是否增加实时解析，应在第一条完整采集／导入路径跑通后单独决定；目前不能承诺自动判断“已全部采集完整”。

## 与产品的接合点

- 产品 `android-shell/app/src/main/java/com/localdatatool/toolbox/MainActivity.java` 已有远端页面白名单、系统分享接收、二进制抓包桥以及同一文件不重复消费的保护。
- `src/pcap/decodeCapture.ts` 已动态加载本地解码器并输出现有导入格式；`src/pcap/readCaptureFile.ts` 仅接受经典 PCAP，PCAPNG 会给出明确错误。原生采集的默认 PCAP 格式可对接，任意外部 PCAPNG 不在第一条链路内。
- 产品壳 `MAX_SHARE_BYTES` 为 32MiB，采集器可保存 128MiB；不能只把两个应用合并就宣称所有抓包可导入。应设计本机文件读取与解析的内存边界，避免整文件 Base64 和重复字节复制，并用真实大文件验证。
- 现有壳 minSdk 23，采集模块基线为 26；需要决定 Android 6/7 保留只看数据还是整体提升最低系统版本。
- 手机上的系统 VPN 一次只能有一个，与使用 VPN 的加速器会冲突；采集从登录前开始，依赖完整握手和仓库／背包数据，不能补造未采集数据。
- 继续保留“本机导入 / 私有云同步 / 手动发布小组”的现有边界。作者云端、令牌、升级强制策略和商人／会员等附属模块无需接入该闭环。
- zdtun 使用 LGPL-3.0-or-later，源码包含修改和许可证说明；复用时保留分库构建、来源、许可证和对应源码。我们现有产品为 GPL-3.0-only。

## 尚不能宣称的结果

尚未构建合并 APK，也没有真机验证采集、断网／撤销 VPN、反复启停、后台杀进程、128MiB 文件解析、当前游戏版本的握手或完整性。因此现在的结论是“有明确可复用路径”，不是“接入已完成”。
