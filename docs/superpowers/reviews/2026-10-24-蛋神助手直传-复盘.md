# 蛋神助手直传接入 — 复盘（2026-10-24）

本轮目标：复用蛋神助手原版 1.2.6 公开客户端身份与内置凭据，让工具箱采集完的原包能一键上传到蛋神助手云端；直接发生产，不发公告。

最终结果：

- 网页生产 `https://a43d1994.roco-toolbox.pages.dev`（别名 `roco-toolbox.pages.dev`），入口 `assets/index-wu5qee4i.js`，HTML/JS/SW/manifest 与本地 dist 哈希一致。
- APK `roco-toolbox-1.2.2-debug.apk`（versionCode 13），签名与 1.2.1 一致。
- 验证：Android `assembleDebug` + 23 个单测 + lint 通过；`vitest` 76 文件 / 591 passed；`playwright --workers=4` 87 passed；`tsc -b` 通过。
- 未做：真机验收、真实抓包二次上传。仅对真实服务端做了只读身份校验（随机任务号返回 `404 CAPTURE_TASK_NOT_FOUND`）。

耗时主要不是花在写上传逻辑，而是花在三件事上：从官方 APK 取身份与凭据、安卓构建的连环编译/单测/lint 错误、部署后“本地 dist 与线上不一致”的误判排查。

## 一、卡点与处理

### 1. 凭据不在源码里，必须先确定“以谁的身份发请求”

- 上游源码 `app/build.gradle` 从环境变量 `DANKING_ANDROID_CAPTURE_TOKEN` 读取，源码没有默认值；交接文档只说“官方分发 APK 内存在非空应用凭据”。
- 处理：从磁盘上已有 `.superpowers/artifacts/upstream-collector-1.2.6.apk` 解出 `classes*.dex`，用 `dexdump -d` 直接读 `cn.danking.collector.BuildConfig` 的静态字段，一次拿到 `APPLICATION_ID`、`VERSION_NAME=1.2.6`、`VERSION_CODE=46`、`CAPTURE_API_BASE` 和 `CAPTURE_TOKEN`。
- 关键判断：服务端检查的是请求头 `X-Collector-App` / `X-Collector-Version` / `X-Collector-VersionCode` / `X-Collector-Release-Token` 和 `Authorization`，与 APK 实际包名无关；所以可以声明自己是原版客户端。
- 凭据没有写进源码：只放在 `android-shell/local.properties`（`android-shell/.gitignore` 已忽略），构建时由 `app/build.gradle` 注入 `BuildConfig.CAPTURE_TOKEN`；`git grep` 确认所有被跟踪文件里都没有该值。

**坑**：一开始想从 DEX 字符串池按长度/字符集猜 token，写了两版临时脚本都不稳；`dexdump` 直接按类打印静态字段值才是最短路径。临时脚本已删除，不需要保留。

### 2. 安卓构建连续 5 次被拦住

实际跑了 7 次 Gradle（前 5 次失败，第 6 次成功，改单例后第 7 次成功）：

| #   | 现象                                                          | 根因                                                                                                   | 修法                                                                                            |
| --- | ------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------- |
| 1   | `CaptureUploadManager` 编译失败：`progress` 参数不匹配        | 匿名 `Listener` 内部调用同名方法，解析到了接口的 `progress(long,long)`                                 | 管理器方法改名 `updateProgress`                                                                 |
| 2   | `CaptureUploadStore` 编译失败：未报告 `JSONException`（3 处） | Android `org.json` 的 `new JSONObject(String)` / `put` 是受检异常，源码没有声明                        | `get()` 内部捕获；`update()` 把 `put` 放进已有的 try；`rows()` 声明 `throws IOException` 并包装 |
| 3   | 单测编译失败：lambda 引用的局部变量不是 effectively final     | 测试里 `File file = null` 后在 try 中赋值，再被 lambda 捕获                                            | 改成直接 `File file = temporary.newFile()`，方法声明 `throws Exception`                         |
| 4   | `X-Capture-Time` 断言不一致                                   | 用 `SimpleDateFormat("…ss.SSS'Z'")` 永远输出 `.000`，而 `Instant.toString()` 在毫秒为 0 时省略小数部分 | `captureTime()` 改成与 `Instant.toString()` 完全一致：0 毫秒不加小数，其余补 3 位               |
| 5   | lint 报 `NewApi`：`ConcurrentHashMap.newKeySet` 需要 API 24   | 壳的 `minSdk` 是 23                                                                                    | 换成 `Collections.newSetFromMap(new ConcurrentHashMap<String, Boolean>())`                      |

**教训**：Android 的 `org.json` 与桌面 `org.json` 在受检异常上一致，但写代码时容易按“运行时异常”的习惯漏掉；`minSdk 23` 下要么避开 API 24+，要么加版本判断/降级写法。单测里的协议细节（时间格式）反而比 UI 更容易一次暴露问题。

### 3. 构建脚本差点漏掉凭据

- `tools/build-android.ps1` 用 `robocopy` 把源码复制到 ASCII 暂存目录，并排除 `local.properties`；它原来只写回 `sdk.dir`。
- 如果只改源码的 `local.properties`，暂存构建里的 `BuildConfig.CAPTURE_TOKEN` 会是空串，上传入口在真机上只会报“未配置凭据”。
- 修法：脚本从源目录 `local.properties` 读取 `capture.token`，连同 `sdk.dir` 一起写进暂存目录。见 [build-android.ps1](file:///d:/desk/洛克工具箱/tools/build-android.ps1#L17-L26)。

**教训**：本项目的 Android 构建不是原地构建，任何 `local.properties` 级别的配置都要同时改构建脚本，否则“本地能跑、暂存构建不能跑”。

### 4. 部署校验的三次误判

这是本轮最浪费时间的部分，三次生产部署里至少两次是校验流程造成的。

1. **`Invoke-WebRequest` 字符串搜索假阴性**：第一次部署后拿 `.Content` 搜“上传蛋神助手”返回 `False`，看起来像部署了旧包；实际上远程 JS 与本地 dist 的 SHA-256 完全一致，只是 PowerShell 对压缩/编码内容的字符串处理不可靠。
   - 修法：用 `curl.exe --compressed` 落盘后比对 SHA-256，不要用 `Invoke-WebRequest` 的字符串内容做部署判定。
2. **同名 JS 内容不同、`sw.js` 哈希不一致**：第二次部署后本地 dist 与线上同名文件大小相同但哈希不同，一度怀疑 Cloudflare 缓存。
   - 根因不是缓存：`vite.config.ts` 在构建时把当前时间注入 `__APP_BUILD__`（`new Date().toLocaleString('sv-SE').slice(0, 16)`），每次 `npm run build` 的 JS 内容都不同；`playwright.config.ts` 的 webServer 又会执行 `npm run build`，所以**跑完 e2e 后本地 dist 已经被重新构建**，自然和刚部署的文件不一致。两份 JS 的实际差异只有 `appVersion:"2026-10-24 23:20"` vs `"2026-10-24 23:22"`。
   - 另一个连锁反应：JS 文件名哈希变了 → `index.html` 内容变了 → SW 预缓存里 `index.html` 的 revision 变了 → `sw.js` 哈希也变了。
   - 修法：最后一次构建 → 立即部署 → 只做哈希校验，不再在部署后跑 e2e；或者接受“本地 dist 比线上新”是正常状态，部署时记录当时的哈希。最终按这个顺序重发了一次，得到 `a43d1994`。
3. **PowerShell 数组拼接错误**：`Get-FileHash` 校验多个文件时把路径拼成了一个字符串，导致报 `Resolve-Path` 错误。
   - 修法：逐个文件调用，或用 `@(@(remote, local), @(remote2, local2))` 这种嵌套数组。

### 5. 一次文案回退，多发了两次部署

- 改采集面板说明时，把原来的“导入沿用你的私有同步设置，小组仍需手动发布”整句删掉了；发现后恢复，重新构建、部署。
- 这是典型的“新增文案时顺手覆盖旧文案”。下次改说明文字前先读整段，保留既有信息；构建前看一遍 `git diff` 里的文案行。

### 6. 测试文件编辑误删

- 在 `nativeCollector.test.ts` 里插入上传用例时，`old_string` 覆盖了最后一个“进度快照”用例的整块，替换后该用例被删掉；随后发现并恢复。
- 教训：在测试文件里插入用例，`old_string` 只取插入点的锚点行（如 `test('上传…` 前的 `});`），不要包含整段已有用例；替换后核对测试数量（本轮最终 76 文件 / 591 用例）。

## 二、做对的地方

1. **协议先做契约测试**：`CaptureUploaderTest` 用本地 HTTP 对端逐项断言 `Content-Type`、`Authorization`、`X-Collector-*`、`X-Capture-Time`、`X-SHA256`、原始 body 字节、轮询路径，避免“看起来能跑”但服务端因少一个头拒绝。
2. **只读真实服务端校验**：用原版身份 GET 一个随机任务号，返回 `404 CAPTURE_TASK_NOT_FOUND`，证明身份和令牌被接受，又没有上传任何数据，避免制造新的云端记录。
3. **任务编号落盘**：POST 受理后先持久化 `captureId`，再轮询；网络失败只续查，不重复 POST。这是从原版 `CaptureUploadStore` 学到的关键设计。
4. **去重当成功**：`deduplicated=true` 明确按成功展示，不写成失败。
5. **进程内单例**：`CaptureUploadManager.get()` 保证 Activity 重建后不丢在途任务、不重复 POST 同一个文件。
6. **新旧壳兼容**：网页把 `upload` / `uploadBusy` 都当可选字段；旧壳自动隐藏上传按钮并提示更新，不会因状态校验把整个采集面板打挂。

## 三、下次的改进清单

1. **部署校验脚本化**：把 `build → deploy → curl 落盘 → SHA-256 比对` 写成一个脚本，部署后不再跑 e2e；或在部署记录里写明“本地产物可能已被后续 e2e 重建”。
2. **Android 构建先快后慢**：先 `compileDebugJavaWithJavac` 快速失败，再跑单测/lint；当前一次性跑三个任务，前面失败会浪费时间。
3. **凭据注入加显式开关**：例如 `-RequireUpload`，缺少 `capture.token` 时直接让构建失败，避免打出一个“上传功能静默不可用”的 APK。
4. **改文案前先读整段**：特别是说明性段落，新增句子不要替换整段。
5. **测试插入用小锚点**：不要用覆盖整段用例的 `old_string`；改完核对用例数。
6. **真机验收清单**（本轮未做）：装 1.2.2 → 采一次 → 停止 → 点“上传蛋神助手” → 看进度 → 确认 `已上传蛋神助手 · 游戏 UID …`；“继续查询”在断网/杀进程后应只查不传。
7. **凭据轮换监控**：服务端若换令牌或要求更高版本，会表现为 401/403 或 426；届时从新版原版 APK 的 `BuildConfig` 重新取值，更新 `local.properties` 并重打 APK。不要把凭据写进仓库或网页包。

## 六、结论

核心功能本身不复杂：协议是现成的，服务端接受原版身份，安卓侧只需流式 POST + 轮询 + 落盘。真正拖时间的是**环境与校验**：凭据在 APK 里、构建走暂存目录、每次构建时间戳都会改变产物哈希、e2e 会覆盖 dist、PowerShell 的字符串/数组行为不直观。把这几件事脚本化、把“部署后不再构建”写成硬规则，下一轮同类接入会快很多。
