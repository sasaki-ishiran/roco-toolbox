# 三方评审：项目健康度与实际价值（2026-10-26）

> 状态：评审完成，结论已归档。优化动作见 [优化升级规划](../plans/2026-10-26-优化升级规划.md)。
> 评审方式：三个独立视角（游戏策划 / 收集型玩家 / 同行开发者）各自只读审查，再由主评审复核证据、合并结论。
> 所有产品决策已由 AI 代为拍板并标注「待审核」，用户可在规划文档的「决策记录」里逐条推翻。

## 0. 一句话结论

**对已经导入数据的人，这是一个真正好用的专业工具；对刚打开的人，它还不是一个产品。**

已经跨过导入门槛的设备只有 13 台，却产生了 157 次成功导入和 626 次看板浏览；另外 59 台设备只打开过一次就再没回来。问题不在算法，也不在功能数量，而在**第一次价值验证**和**回来第二次的理由**。

| 维度 | 分数 | 判定 |
| --- | --- | --- |
| 工程健康度 | **74 / 100** | 良好，但 bus factor = 1、合规有硬伤 |
| 产品健康度 | **64 / 100** | 核心循环成立，留存与呈现偏弱 |
| 增长与实际价值 | **55 / 100** | 价值已在小圈子里证明，服务半径极小 |
| 合规与运营风险 | **52 / 100** | 第三方身份上传、匿名口径、无隐私政策 |
| **综合** | **66 / 100** | **可用、可信、可持续维护；但尚未形成增长闭环** |

**关键判断：**
1. **价值已被证明，但只在 13 台设备里证明。** 人均 12 次导入说明「能导进来的人」会持续用；人均 35 次看板浏览说明结论页确实被反复消费。
2. **流失发生在导入之前，而不是功能不够。** 74% 的设备只开一次，84% 从未导入。
3. **社交是单边的。** 6 个小组全是母本组，种公组和种公资源为 0；需求承接刚上线，还没有任何接单。
4. **单点风险真实存在。** 作者一人维护、无 CI、无错误上报、生产靠本机 wrangler，任何一次离开都会停摆。

## 3. 三方评审结论

### 3.1 策划视角

**判断：核心循环成立，但「目标过载」与「没有节奏」会劝退中度玩家；社交有真实设计，但缺回流与荣誉。**

| 分项 | 分数 | 依据 |
| --- | --- | --- |
| 核心价值 | 88 | 判定链统一、配窝几何 1:1 对齐游戏、换蛋按「能补几格」排序 |
| 目标清晰度 | 70 | 四入口分工清楚，但「母本达标条件 / 展示筛选 / 计划」仍需读文案区分 |
| 留存设计 | 42 | 无趋势、无周报、无成就、无赛季钩子、无通知 |
| 社交协作 | 62 | 共享摘要 + 自动发布 + 需求承接是真设计；缺回流、缺互惠记录、种公组单向 |
| 体验一致性 | 76 | primitives + 交互规范 + 状态语义齐全；文档漂移与信息密度扣分 |
| 可增长性 | 55 | 邀请码是天然增长点，但没有分享物、没有赛季事件 |

主要发现（均已在代码中复核）：

1. **首次价值验证依赖「必须先有文件」**：空态只有「还没有数据」，仓库内无示例数据（`src/ui/EmptyState.tsx`）。
2. **默认目标 42 格，最大 448 格**（`src/domain/coverageTargets.ts`），而小组种公目标上限 256 格（`src/shared/collectionGroups.ts`）。个人口径可能超过小组口径，且 UI 不提示。
3. **留存钩子矩阵几乎空白**：只有「本次新增」、7 天未导入黄条、changelog 弹窗；无周趋势、无目标提醒、无赛季冲刺。
4. **社交只走到「半双工」**：无通知、无「我帮过谁 / 谁帮我」、种公组不能发需求（服务端 `DEMAND_UNSUPPORTED`）。
5. **炫耀动机几乎未满足**：只有文本复制（`CopySheet`），没有可分享的进度卡。
6. **差异化清楚**：上游强在采集/入库，本项目强在规划/决策与小组协作。但覆盖矩阵、种公推荐等能力「一周可抄」，真正的壁垒是实测校准 + 用户网络 + 持续维护。
7. **最需要补的是「收口」**：把全量矩阵变成「本周先做这 3 件」，比再加一个视图更有效。

### 3.2 玩家视角

**判断：算法和口径值得信任，但「第一次用」和「换到之后」两头没接好。**

| 分项 | 分数 | 依据 |
| --- | --- | --- |
| 上手难度 | 55 | 首启不阻断是优点；落在「我的」、无文件来源、导入后不指路 |
| 信任感 | 58 | 本机优先、埋点开关、同步口径写得好；自动共享/第三方上传/默认埋点缺知情 |
| 结果可信度 | 74 | 几何与覆盖度有实测与单测；百分比与「为什么推荐」呈现不足 |
| 日常效率 | 70 | 采集→自动导入很顺；每次要自己找结论 |
| 收集爽感 | 52 | 「本次新增」好看但不持久；进度卡无增量 |
| 社交价值 | 60 | 母本需求承接真能促成交换；种公组无同款链路 |

主要发现：

1. **首启断头路**：导入页只说「采集器里点分享」，但应用内没有采集器获取方式；`README` 与 `docs/手机使用说明.md` 也没有下载入口。iOS 用户没有任何路径说明。
2. **导入成功没有出口**：`ImportOutcomeNotice` 有「去小组查看」，没有「看我还缺什么」；且导入后按 2026-10-25 的决定不自动跳页。
3. **导入中点页签无反馈**：`App.tsx` 的 `navigate()` 在 `importing` 时直接 return，只有底部一个小胶囊提示，容易被当成卡死。
4. **配窝图不可照着摆**：`NestPlanCard` 的图 144px 高、名字截 4 字、无比例尺/图例，`blockedLinks` 只报数量不标线。
5. **百分比口径不清**：「普通 60%」只写在注释里，界面容易被读成「出蛋成功率」。
6. **「已换到」与数据不联动**：勾选只写 `suggestionCardStore`，不写快照；进度不会动，玩家会怀疑工具坏了。
7. **自动共享缺少知情**：导入即自动发布到已加入小组，只有「主动停止共享」的跳过逻辑，没有全局开关，也没有首次同意。
8. **信任文案好但分散**：云同步说明是全应用最清楚的隐私文案；但「数据在哪、谁能看、怎么撤回」分散在三处，没有一页说清。
9. **触区偏小**：种公推荐勾选框 16px、页签 40px 且在顶部，单手操作不友好（与 2026-10-25「全站收紧」的决定有冲突，需要拍板）。
10. **换蛋闭环断在应用外**：复制文本给群聊，应用内没有「把缺口发给某个组员」或「粘贴需求自动解析」。

### 3.3 同行开发者视角

**判断：工程质量明显高于个人项目平均线；但运营与合规风险被低估，项目本身是单点。**

| 分项 | 分数 | 依据 |
| --- | --- | --- |
| 架构 | 80 | domain 真纯函数、shared 层前后端共用、Functions 分层规范 |
| 可维护性 | 72 | 注释一流、无调试残留；但 6 个巨型文件、改动半径大 |
| 测试 | 77 | 领域与并发测试扎实；核心 hook / 解析器 / DB 迁移 / 服务端 sync 零覆盖 |
| 数据管线 | 72 | 原子写、快照、变更报告、wiki 兜底；但 `build-egg-map` / `trim-catalog` 无测试且依赖仓库外输入 |
| 合规安全 | 55 | Android 安全细节做得好；但复用第三方身份上传、无隐私政策、匿名口径不符 |
| 可扩展性 | 60 | 静态前端 + CDN 本身可扩展；15s×3 接口×每请求写库会放大成本 |
| 文档 | 82 | 密度与可追溯性罕见；但多版本并存、过期条目、隐规则未固化 |

主要发现：

1. **巨型模块**（实测行数）：`functions/_lib/collectionGroupsStore.ts` 1,567；`src/ui/useCollectionGroups.ts` 1,140；`src/ui/MotherGroupResources.tsx` 916；`src/domain/nestPlan.ts` 878（`buildNestPlans` 单函数约 700 行）；`ImportPanel.tsx` 588。
2. **测试预算错位**：旧的 `useMotherGroups.ts`（611 行，已不在入口）有 22 个测试；真正在跑的 `useCollectionGroups.ts`（1,140 行）**0 个单测**；`src/api/collectionGroups.ts`（533 行，严格解析）**0 个单测**；`src/storage/db.ts` 的 v1→v2 迁移**0 个测试**（用户数据丢失级路径）。
3. **测试与主线脱节**：根 `vite.config.ts` 明确排除 `tools/**`，管线测试用独立 `package.json`，其中 `egg-fallback.test.mjs` 还用 `node:test`，`npm test` 永远跑不到。
4. **构建不检查后端**：`npm run build` = `tsc -b && vite build`，根 `tsconfig` 不含 `functions/`；后端类型错误可以通过构建。
5. **无 lint、无 CI、无错误边界**：仓库无 `.eslintrc*`、无 `.github/`、无 `ErrorBoundary` / `unhandledrejection`；只有 8 个埋点事件，没有 error 事件。
6. **后端写放大**：`useCollectionGroups` 每 15 秒拉详情 + 任务 + 需求（3 请求）；`authenticate()` 每请求 `UPDATE tokens`，`rateLimit()` 每请求 UPSERT。免费额度下，长时间挂小组页的重度用户会先触顶。
7. **合规硬伤**：
   - `CaptureUploader.java` 硬编码上游端点、包名、版本、双令牌头，以第三方客户端身份上传玩家抓包；UI 只提示「会上传到云端」，未披露身份复用。
   - 埋点文档写「匿名 deviceId」，但 `functions/_lib/events.ts` 在有登录态时会写 `account_id`。
   - `README` 与 `docs/部署到公网.md` 仍写「账号数据只存在本机」，与云同步/小组共享冲突。
   - 无隐私政策/用户协议页面；GPL 源码可得性依赖 GitHub 仓库公开。
8. **代码是能维护的，项目不是**：环境、凭据、赛季数据、安卓签名、领域口径全在一人手里；换一台机器无法按 README 复现发布。

## 4. 交叉验证：共识、分歧与裁决

### 4.1 三方共识（按重要性）

1. **价值门槛在「导入之前」**：三方都指向同一件事——新用户拿不到文件，就永远看不到结论。线上 16% 的导入率是直接证据。
2. **留存缺钩子**：没有趋势、没有「今天做什么」、没有回访事件。收集类产品最基础的「看得见的成长」缺失。
3. **社交只完成一半**：母本组的需求承接是真设计，但种公组 0 采用、通知缺失、互惠无记录。
4. **结果呈现不可验证**：百分比、配窝图、推荐理由都「算得对但看不懂」，削弱信任与传播。
5. **工程强、单点弱、合规有硬伤**：这不是代码质量问题，而是运营与风险问题。

### 4.2 分歧与裁决（已代拍板，待用户审核）

| # | 议题 | 分歧 | 裁决 | 理由 |
| --- | --- | --- | --- | --- |
| J1 | 是否继续加功能 | 策划建议先做留存功能；同行建议先补测试与合规 | **先修转化与闭环，暂停新玩法** | 16% 导入率下，新功能只服务 13 台设备，边际收益最低 |
| J2 | 是否重写/大重构 | 同行点名 6 个巨型文件 | **不重写、不换栈、不拆包；只拆边界** | 领域层稳定且有测试，重写风险远大于收益 |
| J3 | 种公组需求承接 | 策划建议补齐；线上数据显示种公组 0 | **暂不做，先验证采用** | 没有用户就不该先建复杂协作 |
| J4 | 第三方上传 | 同行列为最高危；玩家认为有卖点但需知情 | **保留能力，默认不打包凭据，UI 明示身份** | 尊重用户此前明确要求，同时降低暴露面 |
| J5 | 示例数据 | 策划强烈建议；玩家担心误导 | **做只读示例，明确标注「示例，不保存」** | 转化收益最大，成本可控；只要隔离存储即可 |
| J6 | 自动发布 | 玩家要开关；策划认为自动发布是正确的 | **保留自动发布 + 全局开关 + 首次告知** | 取消会回到「忘记发布」的老问题 |
| J7 | 文档治理 | 同行建议全量归档成 4 份活文档 | **只做纠错与最小单一事实源** | 全量迁移成本高、收益低，且容易丢历史结论 |
| J8 | 触区放大 | 玩家要求放大；用户此前要求全站收紧 | **只放大高频高风险控件**（勾选框、接单、header） | 不做全站回退 |
| J9 | 埋点关联账号 | 同行要求去关联；策划希望保留分析能力 | **默认不关联账号，彻底匿名** | 与文档承诺一致，避免信任危机 |
| J10 | 是否加 CI | 同行建议 | **先加本地 `npm run verify` + 发布脚本；CI 暂缓** | 当前无协作方，本地门禁收益更高 |

### P0（不做会持续漏人 / 漏数据 / 冒合规风险）

| ID | 问题 | 证据 | 影响 | 建议 | 成本 |
| --- | --- | --- | --- | --- | --- |

## 6. 健康度与实际价值判定

### 6.1 评分汇总

| 视角 | 综合分 | 最狠的一句话 |
| --- | --- | --- |
| 策划 | 65 | 「技术上可持续维护，产品上可被替代；最危险的是用户没有理由每周回来。」 |
| 玩家 | 62 | 「安卓 + 装好壳的人会觉得值；iOS 和只想点点看的人，第一步就走了。」 |
| 同行 | 74 | 「代码是能长期维护的，项目不是——bus factor = 1。」 |
| **主评审综合** | **66** | **价值真实但半径极小；瓶颈是转化与留存，不是功能。** |

### 6.2 实际价值公式

一个工具类产品的实际价值 ≈ **触达 × 首次成功 × 复用频率 × 不可替代性**。

| 因子 | 现状 | 判断 |
| --- | --- | --- |
| 触达 | 80 台设备 | 很小，但都是精准的孵蛋党 |
| 首次成功 | 16% | **最大短板** |
| 复用频率 | 导入用户人均 12.1 次，看板人均 35 次 | **强** |
| 不可替代性 | 配窝几何 + 小组协作 + 多账号规划 | 中-强，算法可抄、实测结论与用户网络难抄 |

结论：**乘数被「首次成功」压住了。** 如果把导入率从 16% 提到 35%，在触达不变的情况下，有效用户接近翻倍；这比再加三个功能更划算。

### 6.3 三类用户的实际价值

| 用户 | 现状 | 价值 |
| --- | --- | --- |
| 安卓 + 已装壳的孵蛋党（核心 13 台） | 采集→自动导入→看板闭环 | **高**：日常效率工具，替代手工记账 |
| 网页 / iOS / 群里点开的新人（59 台只开一次） | 拿不到文件、不知道下一步 | **接近 0**：只看到「导入游戏数据」 |
| 小组组织者（6 组 / 14 人） | 母本资源可对照、可发需求 | **中**：母本侧成立；种公侧 0 使用 |

### 6.5 最危险的三个未验证假设

1. **M1 多路径模型**：配窝算法建立在「公母连线越多、命中机会越大」的假设上，`project_memory` 自己写了 M2 未证实。如果模型错了，最核心的建议会系统性偏差。
2. **上游不会覆盖规划层**：蛋神助手目前强在采集/入库；一旦它补上覆盖度或配窝，本项目的差异化会被顺手覆盖。
3. **玩家愿意为效率装 APK**：安卓侧载 + 同签名 + 卸载丢数据，是一道真实门槛；iOS 用户完全无法使用。

## 7. 结论：保留什么、停止什么、开始什么

### 保留（不要动）

- `src/domain/` 的纯函数分层与统一判定链（`cellStateFor`）。
- 1:1 对齐游戏的配窝几何（`NEST_SIZE=8 / PAIR_RANGE=17 / GROUP_GAP=24`）与 M1 下的分配口径。
- 「共享摘要而非整包」的小组隐私设计。
- 导入后自动云同步 / 自动发布的产品判断（要加开关，但不要取消）。
- changelog + 教程版本 + 双分支发布这套节奏。

### 停止

- 在首次转化修好之前，继续加新玩法（成就、种公承接、赛季系统）。
- 带脏工作区直接发生产。
- 用「匿名」描述会关联账号的统计。

### 开始

1. **价值闭环**：示例看板、文件获取指引、导入后出口、自动共享开关。
2. **可观测**：漏斗事件、D7 留存、错误边界、发布脚本。
3. **合规最小集**：隐私说明页、第三方上传披露、修过期承诺。
4. **可信呈现**：配窝图可读、百分比口径、推荐理由。
