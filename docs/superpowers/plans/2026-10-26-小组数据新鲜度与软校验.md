# 小组数据新鲜度与软校验策略

> 并入《统一收集小组》方案，作为发需求 / 接单校验的前置规则。
> 目的：不让「某个人忘记导入发布」把正常玩家的发需求、接单卡死。

## 1. 问题

- 发需求、接单都依赖组员发布的亲本档案。
- 只要有人没更新，系统就可能误判「组里没人能孵」，从而不让发需求、不让接单。
- 人越多，越难等所有人更新；硬限制会伤害正常使用。

## 2. 原则

1. **区分「确认没有」和「数据不全」**：数据旧 ≠ 没人能孵。
2. **只有确认没有才硬拦**：所有相关账号都新鲜、且确实没有现货/可孵，才不让发。
3. **数据不全时软提示**：提示「可能有人能孵但没更新」，用户确认后仍可发布/接单。
4. **接单看自己的数据**：别人旧不旧不影响我能不能接；我自己数据旧时提示后仍可接。
5. **不自动刷新后硬拦**：刷新是用户动作，不是拦截理由。

## 3. 新鲜度定义

| 项         | 规则                                                                            |
| ---------- | ------------------------------------------------------------------------------- |
| 依据       | 发布资源的 `sourceExportedAt`（导出时间），不是发布时间；重新发布旧数据不算新鲜 |
| 新鲜       | 导出时间在 7 天内                                                               |
| 旧         | 超过 7 天                                                                       |
| 未发布     | 从没发布过，按「旧 / 未知」处理                                                 |
| 粒度       | 按账号判断；一个成员多个账号时，每个账号单独算                                  |
| 展示       | 成员行显示「N 天未更新」；组头显示「已更新 X/Y 人」                             |
| 旧数据兼容 | 老摘要没有导出时间，按「旧」处理，提示重新导入发布                              |

> 7 天与现有「N 天未更新」红色提醒保持一致。

## 4. 状态模型

按当前需求口径（蛋 + 性别 + 性格 + 体型 + 声音，空字段跳过）计算：

| 状态     | 含义                                            | 发需求               |
| -------- | ----------------------------------------------- | -------------------- |
| 有现货   | 某成员新鲜账号里已有匹配个体                    | 允许                 |
| 可孵     | 某成员新鲜账号里有母 + 公，能配出               | 允许                 |
| 缺另一只 | 新鲜数据里只有母或只有公，配不成                | 不允许（数据已确认） |
| 数据不全 | 没有任何新鲜供给，且至少一个相关账号旧 / 未发布 | **提示后允许**       |
| 都没有   | 所有相关账号都新鲜，确实没有任何供给            | 不允许（数据已确认） |

- 计算时排除需求方自己：自己能孵就不需要发需求。
- 如果只有需求方自己有供给，提示「你自己就能孵」并拦住。
- 只要有一个相关账号是旧的，就不能下「都没有」的结论，只能标「数据不全」。

## 5. 发需求流程

1. 按当前口径算状态：
   - 有现货 / 可孵 → 正常可发。
   - 缺另一只 / 都没有（全新鲜）→ 红边，不能发，提示「全组最新数据里没人能孵，等组员更新后再试」。
   - 数据不全 → 黄边，可点，但弹确认：
     「有 2 人超过 7 天未更新，可能有人能孵但没发布。仍要发布？」
2. 用户确认后按最终条件再校验一次：
   - 仍是数据不全 → 允许发布。
   - 刷新后变成全新鲜且没有供给 → 拦住。
3. 发布成功后，需求卡带「组内数据不全」标记，提醒承接人可能还没更新。

## 6. 接单流程

| 我的数据           | 展示                                 | 接单         |
| ------------------ | ------------------------------------ | ------------ |
| 新鲜 + 有现货/可孵 | 正常出现在「我能接的」               | 允许         |
| 新鲜 + 没有匹配    | 不出现                               | 不能接       |
| 旧 / 未发布        | 出现在「数据未更新，可能能接」折叠区 | 提示后允许接 |

- 别人数据旧不影响我接单；只看我自己的数据。
- 我数据旧时提示：
  「你的数据 12 天未更新，系统无法确认你能孵；建议先导入。仍要接单？」
- 接单成功后，需求方看到「承接人数据 12 天未更新」，可以自行跟进。
- 服务端仍只校验权限；新鲜度与库存校验在客户端，属于防手误，不防作弊。

## 7. 页面提示

| 位置         | 文案                                                       |
| ------------ | ---------------------------------------------------------- |
| 组头         | `数据完整度 8/10 · 2 人超过 7 天未更新`                    |
| 成员行       | `12 天未更新`（红） / `未发布`（灰）                       |
| 缺口卡       | `数据不全 · 可能有人能孵`（黄）                            |
| 发需求确认   | `有 2 人超过 7 天未更新，可能有人能孵但没发布。仍要发布？` |
| 全新鲜无供给 | `全组最新数据里没人能孵这只；等组员更新后再试。`           |
| 接单确认     | `你的数据 12 天未更新，系统无法确认你能孵；仍要接单？`     |
| 需求卡       | `组内数据不全` / `承接人数据 12 天未更新`                  |

## 8. 边界

- 不因为数据旧自动刷新后硬拦；刷新只更新展示，是否发布由用户确认。
- 不要求所有人更新才能用；只有「全新鲜 + 确实没有」才硬拦。
- 旧摘要没有导出时间 → 按旧数据处理，不会误判为「都没有」。
- 多账号：只要有一个相关账号旧，就不能下「都没有」结论。
- 需求方自己数据旧：仍可发布，按「数据不全」提示。
- 承接人数据旧：仍可接单，提示后确认；需求方可见。
- 组里没人更新且确实没有供给：发不了；这是唯一会硬拦的「没人能孵」场景。

## 9. 验收

- 全组新鲜、没人能孵 → 红边，不能发。
- 有 1 人超过 7 天未更新、没人能孵 → 黄边，确认后可发。
- 有人新鲜可孵 → 正常可发，不提示数据不全。
- 我数据旧、可能有匹配 → 出现在「数据未更新，可能能接」，确认后可接。
- 我数据新鲜、没有匹配 → 不在「我能接的」，不能接。
- 别人数据旧但我的数据新鲜 → 不影响我接单。
- 重新发布 30 天前导出的数据 → 仍按旧数据算，不能变成「新鲜」。
- 全组新鲜、只有我自己能孵 → 提示「你自己就能孵」，不能发。
