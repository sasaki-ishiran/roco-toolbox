# 多设备数据合并 · 方案

**日期**：2026-10-03
**状态**：网页部分已实施并部署（2026-10-03 20:01）；壳部分：「用其他应用打开」入口已随 1.1.3 补上（见 §2.4），导出修复与字节通道待并入 1.1.4
**触发**：朋友在平板与手机各导入了一份数据，发现两边不能一起看到。多数孵蛋玩家是多设备登录的。

## 0. 为什么现在不行（两个叠加的问题）

1. **「导入备份」是整体覆盖，不是合并**。[snapshots.ts](../../../src/storage/snapshots.ts) 的 `replaceAllSnapshots()`
   先 `clear` 再 `write`——在平板上导入手机的备份，**平板原本那份数据会被清掉**。
   所以现状不是「看不到对方的数据」，而是两台设备的数据**互斥**。
2. **APK 里「导出全部数据」是坏的**（`blob:` 下载在 WebView 里被静默忽略，见
   [验收反馈整改 §10](2026-10-03-验收反馈整改.md)），已定 1.1.4 修。

## 1. 本次范围（用户 2026-10-03 拍板）

**做**：

1. 「导入备份」改成**合并**：同账号取**导入时间较新的那份**，本地独有的账号一律保留。
2. **支持把备份分享给应用直接导入**（用户追加）：微信/QQ 收到 json → 分享给「洛克工具箱」→ 自动按合并导入。
   手选文件也走同一套识别，不再要求「必须点对按钮」。

**不做**：云端同步（Workers + 同步码）。它会改变「数据只存在本机」的隐私承诺，属于独立议题；
本方案的合并规则是它的前置，将来上云不用重做。

**语义依据**：一份快照就是「该账号在导入那一刻的全量」（真实抓包是整包导出，
`computeAddedPets` 的注释也写明「放生掉的精灵只是从新数据里消失」）。
所以取较新的那份与现有语义一致，而求并集会让放生掉的精灵「复活」。

## 2. 设计

### 2.1 领域层：`mergeSnapshots()`

新增纯函数（放 [backup.ts](../../../src/domain/backup.ts)）：

```ts
export interface MergeResult {
  snapshots: AccountSnapshot[];
  /** 本地没有、备份里有的账号 */
  added: string[];
  /** 两边都有、备份里的更新 → 已替换 */
  updated: string[];
  /** 两边都有、本地的更新或无法比较 → 保留本地 */
  kept: string[];
}

export function mergeSnapshots(
  local: AccountSnapshot[],
  incoming: AccountSnapshot[],
): MergeResult;
```

| 情况                                     | 处置                                                    |
| ---------------------------------------- | ------------------------------------------------------- |
| 备份里有、本地没有                       | 并入（`added`）                                         |
| 本地有、备份里没有                       | **保留本地**（不删！这是与现在最大的差别）              |
| 两边都有，备份的 `importedAt` 更新       | 用备份的替换（`updated`）                               |
| 两边都有，本地的 `importedAt` 更新或相同 | 保留本地（`kept`）                                      |
| 任一侧 `importedAt` 为空或不可解析       | **保留本地**并计入 `kept`（不用时间不明的数据覆盖本地） |

### 2.2 一个入口认两种文件

现在 `handleImport` 拿到 JSON 后**无条件**按抓包解析（`parseBackup`），所以分享/选中一份工具箱备份会报错。
改成先判类型：

```
readCaptureFile(file)
  ├─ PCAP  → 采集器解析器 → 抓包导入（不变）
  └─ JSON  → isToolboxBackup(raw)?
              ├─ 是 → 合并导入（mergeSnapshots）
              └─ 否 → parseBackup → 抓包导入（不变）
```

这一步同时覆盖**三条入口**，行为一致：

1. 手动点「导入抓包数据」选文件
2. 浏览器里分享给网页（Web Share Target）
3. 安卓壳接住系统分享（微信/QQ → 分享 → 洛克工具箱）

壳侧**不需要改判定**：备份 json 不是 PCAP，壳会按文本注入；网页侧收到的仍是 File。
（但当时漏了入口本身：微信 / QQ 的「用其他应用打开」走 VIEW 意图，壳没注册，手机上同样找不到——
已在 1.1.3 补上，见 §2.4。）

### 2.3 UI 文案

- 「导入备份」按钮改名 **「合并导入」**；确认框讲清规则（同账号取较新、本地独有的账号保留）。
- 反馈文案分清来源：`已合并导入：新增 N 个账号 · 更新 M 个 · 保留本地较新的 K 个`；
  「导入抓包数据」识别出是备份时，额外说明一句「这是工具箱备份，已按合并导入处理」。
- **不再提供「整体覆盖」开关**：要覆盖就先用「重置导入数据」清空再合并导入，语义仍可达，少一个模式。
- 「导入备份」选到抓包文件时，仍给可读报错（现状保留）。

### 2.4 壳侧的三个改动

1. **补「用其他应用打开」入口**（✅ 已随 1.1.3 发布）：微信 / QQ 点开文件走的是 VIEW 意图
   （文件挂在 intent.data 上），壳此前只注册了 SEND——这条路径的「打开方式」列表里根本没有本应用，
   手机上同样找不到（2026-10-03 真机反馈）。已在 AndroidManifest 补 `ACTION_VIEW`
   （scheme 限 content / file，类型 `*/*`），`MainActivity.handleShareIntent` 同时处理 intent.data；
   回归守卫 `src/share/androidShell.test.ts`。
2. **导出修好**（待做，并入 1.1.4）：加 JS 桥，原生用 `MediaStore.Downloads` 写到系统下载目录（Android 10+ 免权限）。
3. **分享进来的文件一律走字节通道**（待做，并入 1.1.4）：现在壳对非 PCAP 的分享文件是
   `decodeText` 后经 `evaluateJavascript` 注入文本（[MainActivity.java](../../../android-shell/app/src/main/java/com/localdatatool/toolbox/MainActivity.java)）。
   真实备份 json 可能有 1~3 MB，这么大的字符串注入既慢又可能被截断。
   改成与抓包同一条路：字节留在壳里，网页从拦截地址取（`roco-share.invalid`）。
   纯文本分享（`EXTRA_TEXT`，没有文件）仍走注入，那条本来就没有大小问题。

## 3. 两台设备怎么用（最终效果）

```
手机：导出全部数据（1.1.4 起直接存到「下载」目录）
  → 微信发给自己 → 平板上打开该文件 → 分享/用其他应用打开 → 洛克工具箱
平板：自动合并导入 → 平板同时拥有 自己的 + 手机的 账号
平板：再导出一次发回手机 → 手机合并导入 → 两边完全一致
```

因为导出的是**全量**，双方各导入一次即双向对齐；而且「分享给应用」这条路省掉了找文件。

## 5. 验证

- 单测：并入 / 保留本地独有 / 更新 / 保留较新 / 时间不可比较时保留本地 / 空备份不改变本地。
- e2e：
  - 导入 `backup-sample`（测试甲）→ **合并导入** `backup-sample-2`（测试乙）→ **两个账号都在**
    （当前实现下第二个会顶掉第一个，这条会失败）。
  - 现造一份「同账号、更早 `importedAt`」的备份 → 合并后本地那份不被覆盖。
  - 把备份文件塞进「导入抓包数据」入口 → 按合并导入处理并给出说明。
- `npx tsc -b` / `npx vitest run` / `npx playwright test` 全绿。
- 真机（1.1.3）：微信 / QQ 收到 json →「用其他应用打开」→ 洛克工具箱 → 合并导入成功。
- 真机（1.1.4）：大备份（>1 MB）不截断。
