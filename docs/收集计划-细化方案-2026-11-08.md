## 1. 计划卡偏大、窄屏溢出

**现在的问题（原型侧）**：旧原型的卡是固定宽 `343px` + 绝对定位（每个元素写死 `left/top`），
计划卡高度写死 `142px`。在 375 屏上刚好贴边，在 390 屏上卡比容器窄 15px，
再叠加演示页自身 `body` 的固定宽度，窄屏会出现横向滚动；卡内文字一长只能靠 `nowrap` 硬顶。

**改法**：计划卡改成**流式布局**，不再有绝对坐标：

| 项 | 旧 | 新 |
| --- | --- | --- |
| 卡宽 | 固定 343px | `width:100%`（跟随 375 / 390 的内容宽） |
| 卡高 | 固定 142px | 随内容自适应，常态 112~132px |
| 卡内结构 | 5 个绝对定位元素 | 4 段：头像+名称/状态 → 条件行 → 徽标流 → 操作 |
| 内边距 / 圆角 / 卡间距 | 12 / 16 / 10 | 10 / 14 / 8 |
| 长文本 | `nowrap` 顶出边界 | 单行 `ellipsis`，点卡看详情 |

**为什么**：宽度跟屏宽走，390 不会出现「卡比容器窄」的错位；高度自适应后，有无认领人备注都不撑破。
配色沿用现有语义（母粉 / 公蓝 / 体型绿 / 声音琥珀），见第 5 点。

原型里已按 375 / 390 两档实际截图验证（见文首两张图）。

## 2. 「添加想收」怎么设计：复用现有需求卡

**现有那张卡**：[DemandPublishSheet.tsx](../src/ui/DemandPublishSheet.tsx)
（`L41-L66` 定义 props / 表单状态，`L84-L100` 初始化 + `defaultCriteria` 预填，`L166-L181` 提交）。
它现在负责「发布 / 编辑需求」，卡里是：

- 蛋网格（选中后显示蛋头像 + 名字，可多选蛋）；
- 每颗蛋的性格 chips（可多选，空 = 不挑）；
- 统一一组「性别 / 体型 / 声音」（从 `defaultCriteria` 预填，可改）；
- 「是否要求绿窝」开关；
- 底部按钮：发布 N 条需求。

提交走 [publishCollectionDemand](../src/api/collectionGroups.ts#L630-L652)：`POST /api/collection-groups/{groupId}/demands`。

**复用方式（推荐）**：给 `DemandPublishSheet` 增加一个 `mode` 入参，不另造表单：

| 字段 | 发需求模式 | 添加想收模式 |
| --- | --- | --- |
| 蛋网格 | 必选，可多选 | **保留**（复用同一套网格与搜索） |
| 性格 chips | 必选 / 可不挑 | **收窄掉**：不在这里选 |
| 性别 / 体型 / 声音 | 可改 | **收窄掉**：只读展示小组口径默认值 |
| 绿窝 | 可选 | 收窄掉 |
| 标题 / 主按钮 | 「发布需求」 | 「添加 N 条想收」 |

**为什么这么收窄**：计划是**蛋级**（`collection_plans` 只有 `egg_game_id`），不存性格 / 性别 / 体型 / 声音。
性格在计划卡上显示的是「这颗蛋还缺哪些性格」，由现有覆盖度现算（见第 5 点），
不需要用户在添加时再选一遍；性别 / 体型 / 声音是「发需求」时才需要的信息，
所以在想收阶段只展示小组口径默认值，真正发需求时再打开完整卡预填。

**批量导入全部缺口**：**不弹卡，直接落库**。

- 缺口来源复用现有计算：[MotherGroupResources.tsx](../src/ui/MotherGroupResources.tsx#L553-L563)
  用 `targetRows` 过滤 `missingNatures.length > 0` 的蛋；
- 批量写入一次请求（`POST .../plans/batch`），全部落 `active`（进行中）——2026-11-09 用户决策：
  进行中不设数量上限，批量导入与「开始」一致，不再先落 backlog；
- 已完成的蛋跳过（用户口径③）：已有 `done` 计划或这颗蛋的归档记录时不再导入，
  除非用户手动点「＋ 添加想收」；
- 结果只给一句提示：「已导入 5 条进行中（已完成的 3 颗已跳过）」，不打断操作。

**为什么批量不弹卡**：缺口动辄几十条，逐颗弹卡会把「攒着」变成负担；
原型里点「批量导入全部缺口」已经演示了这个结果提示。

## 3. 「上窝匹配」：不做自动判定，只做「认领人勾 → 发布人确认 + 快照提示」

**现有能力**（都已确认，不需要新接口）：

| 能力 | 位置 | 能提供什么 |
| --- | --- | --- |
| 本机「已上窝」记忆 | [demandPlacementStore.ts](../src/ui/demandPlacementStore.ts#L9-L80) | `localStorage`，key 为 `roco.demandPlacements:<云账号 accountId>`；单行 key 含 `groupId / demanderAccountId / demandKey / claimedAt`，所以同需求重发后旧勾选不会串。**跟云账号走，不跟设备整体走**。 |
| 家园快照 | [types.ts](../src/domain/types.ts#L105-L166) 的 `HomeNest / HomeResident / HomeSnapshot`；快照挂在 [AccountSnapshot.home](../src/domain/parseBackup.ts#L29-L44)，按 `accountKeyOf`（游戏 UID）分账号存 | 每个游戏账号各一份，带 `capturedAt`、`nests`（含 `nestType: 'academy'` 学院小窝）、`residents`（含 `baseId / name / nature / gender`）。**来自抓包，不是实时查询**。 |
| 刷新家园 | [Home.tsx](../src/ui/Home.tsx) + [useHomeRefresh.ts](../src/ui/useHomeRefresh.ts) | 刷新 / 增量合并入口；网页端只读已有快照，不能主动拉线上家园。 |
| 手动候选配对 | [demandPlacementStore.ts](../src/ui/demandPlacementStore.ts#L90-L122)、[HomeDemandPlacements.tsx](../src/ui/HomeDemandPlacements.tsx#L196-L254) | 「用哪颗蛋 / 哪只公接单」的本机偏好，跟匹配判定是两件事。 |

**方案（不做自动判定）**：

1. 认领人在需求卡勾选「已上窝」→ 调 `POST .../demands/placement` 写服务端 `placed_at`
   （新增列已在 `functions/schema.sql` 与迁移里备好）。
2. 发布人在「我的收集」看到第 4 步「待我确认」高亮 → 手动点「去确认」结单。
3. 家园快照只做**提示**，不阻断：
   - 认领人勾选时，如果本机所有快照里，最新一次该游戏账号的家园 `residents` 里没有这个蛋
     （用 `baseId` 映射蛋 gameId），提示一句「你最近一次家园快照（10-29）里还没有这只，确认已经放好了吗？」；
   - 快照超过 24 小时就带上日期，避免用户以为系统在实时校验。
4. **多账号怎么处理**：
   - 本机记忆现在按**云账号**隔离，但上窝动作是**某个游戏账号**做的；
   - 建议服务端 `placed_at` 旁再记一个可空的 `placed_by_account_key`（`uid:<gameId>`），
     发布人就能看到「阿乙 · 账号② 已上窝」，多账号用户不用猜是谁放的；
   - 提示只认「该游戏账号」的快照，不拿另一个账号的家园数据误判。

**为什么不做自动判定**：没有查线上家园的接口，多账号还要切号再刷新；
自动判定会把「没抓到快照」误判成「没上窝」，反而增加解释成本。

## 4. 小组基础设置放哪里

**现在在哪**：[CollectionGroups.tsx](../src/ui/CollectionGroups.tsx#L224-L318) 的组卡片里，
依次是 `GroupSwitcher`（切换 / 新建 / 加入）、组名 / 类型 / 人数 / 刷新、
`PublicationCard`（我的共享资源）、[MotherGroupMembers](../src/ui/MotherGroupMembers.tsx#L41-L44)
（成员列表、邀请码、组长重置 / 解散、普通成员退出）。这些目前都在「小组」页顶部展开，
跟「我缺的 / 需求中心 / 共同寻找」挤在同一屏。

**方案**：不新开顶级页面，在小组页**组头右侧加一个「设置」按钮**（原型已画），点开底部抽屉，分五块：

1. 组名与类型（类型只读，组名组长可改）
2. 成员与邀请（沿用 `MotherGroupMembers`：成员、邀请码、重置、移除）
3. 我的共享资源（沿用 `PublicationCard`）
4. 切换 / 新建 / 加入小组（沿用 `GroupSwitcher`）
5. 退出 / 解散（沿用现有的确认流程）

**为什么**：这些是「这个组」的属性，跟着组走；放「我的」页会让用户跨页找，
而且「我的」页现有分区只有身份 / 数据 / 同步（[Profile.tsx](../src/ui/Profile.tsx#L20-L24)、
[navigation.ts](../src/ui/navigation.ts#L13-L21)），加「小组设置」会把两个信息层级混在一起。
组头常驻一个「设置」也不会占用主视图的注意力。

## 5. 体型 / 声音 / 公母的展示

**每处展示的字段与压缩方式**：

| 位置 | 展示内容 | 压缩方式 |
| --- | --- | --- |
| 我的收集 · 计划卡 | 缺哪些性格 + 公母 + 体型 + 声音 | 一条条件行，10.5px 小 chip，超出省略；点卡看全 |
| 想收列表 | 只显示「缺 X」（性格） | 一行，右侧「开始 / 删除」 |
| 组内广场 · 你能补的 | 成员名 + 缺的性格 + 公母 + 体型 + 声音 | 两行：谁 + 条件行 |
| 组内广场 · 成员计划 | 蛋名 + 条件行 + 状态标签 | 条件行同计划卡 |
| 求助中的需求 | 蛋名 + 缺的性格 + 公母 | 小卡，第三行是承接状态 |

**数据从哪来**：

- 有未结单需求 → 直接用需求行上的 `nature / gender / body / voice`（沿用现有
  [matchesParentGrade / petMatchesDemand](../src/domain/demandCriteria.ts#L84-L103) 的口径）；
- 没有需求 → 用小组口径默认值（现有 `motherTargetLabel` 那套）+ 缺口性格
  （[MotherGroupResources.tsx](../src/ui/MotherGroupResources.tsx#L366-L383) 的推荐性格 / 目标口径）。

**缺省值**：空字符串统一显示「不限」，不隐藏；计划卡永远有这一行，避免用户以为「这颗蛋不需要条件」。

**为什么放一行**：孵蛋条件只有四个短词，一行 chip 的信息密度最高，
也不会把 8.5px 的徽标流挤掉；详情页再展开完整解释。

## 6. 「你能补的」能不能复用现有匹配

**现有匹配都在「个体级」**：

| 现有实现 | 位置 | 输入 | 与「你能补的」的差异 |
| --- | --- | --- | --- |
| `matchesParentGrade` / `petMatchesDemand` | [demandCriteria.ts](../src/domain/demandCriteria.ts#L84-L103) | 本机精灵个体（体型 / 声音 / 性格 / 性别） | 需要完整精灵快照；「你能补的」只需要「这颗蛋你有没有」 |
| `resolveTarget` / `isMotherCandidate` | [demandPlacement.ts](../src/domain/demandPlacement.ts#L181-L227) | 本机快照 + 需求 | 面向「用哪只接单」，不是广场推荐 |
| `preferredPair` 手动配对 | [demandPlacementStore.ts](../src/ui/demandPlacementStore.ts#L90-L122) | 本机选择记忆 | 是用户手动指定，不是自动匹配 |
| 覆盖度 / 母本口径 | `MotherGroupResources` 的 `targetRows` / 缺口计算 | 组目标 + 我的覆盖 | 回答「我缺什么」，不是「我能补谁」 |

**结论**：不能共用「个体级」实现，但可以共用数据源。

- 已实现的新纯函数：[collectionPlans.ts](../src/shared/collectionPlans.ts) 的 `matchablePlanEggIds`，
  输入是「我发布过的蛋 gameId 集合 × 别人 active 计划」，按蛋去重（已有 26 条测试）；
- 数据源复用现有共享摘要：[motherGroups.ts](../src/shared/motherGroups.ts#L83-L104)
  的 `SharedMotherAccount.eggGameIds` / `SharedProductionLine`（服务端 `mother_group_accounts.egg_game_ids`），
  服务端直接算，不依赖任何人的本机快照；
- 差异：精度从「个体」降到「蛋」（这是产品要的：先说「我有这颗蛋」），**但仍受产线约束**：
  2026-11-09 用户口径确认，「你能补的」优先用 `lines_json` 的产线判断目标体型 / 声音 / 性格能不能产，
  只有旧摘要没带产线时才退回「有任意母本」；不能把「图鉴里有这颗蛋」当成「我能补」。
  且不需要图鉴 / 精灵库参与，函数可以在 Functions 里直接跑。

**为什么新写**：现有匹配都依赖浏览器里的精灵数据，服务端拿不到；
硬套会把「你能补的」绑死在单机，失去组内共享的意义。

### 卡面留了什么 / 二级页放了什么

| 位置 | 卡面（只这些） | 二级页 |
| --- | --- | --- |
| 我的收集 | 头像 + 蛋名 + 状态徽标 + 条件一行（公母/体型/声音/缺的性格）+ 一个主按钮 + 「详情 ›」 | 条件全量、5 步进度、需求与承接人、提供者备注、改备注、删除 |
| 组内广场 · 你能补的 | 头像 + 蛋名 + 谁的收集 + 条件一行 + 「我能提供」 | 发布人、进度、提供者与备注 |
| 组内广场 · 成员计划 | 头像 + 蛋名 + 成员名 + 条件一行 + 状态 | 同广场二级页 |

密集文案（口径说明、括号补充、历史解释）已从卡面删除，只保留状态词与条件词。

### 高频操作有没有被藏进二级页

结论：**没有**。开始、发需求、去确认、我能提供都留在卡面（一个实心主按钮 + 一个「详情 ›」次级入口）；
二级页只放低频的改备注、看提供者、删除与时间线。
理由：这四件事是进小组就会做的，藏进二级页会把一次点击变成两次；反过来，
改备注 / 删除一周也用不到一次，放二级页不会增加日常成本。

## 8. plans 接口清单（已实现，未提交 / 未部署）

所有接口都要求是组员；非组员返回 403 `NOT_MEMBER`，组不存在返回 404 `GROUP_NOT_FOUND`。

| 方法 | 路径 | 入参 | 出参（一句话） |
| --- | --- | --- | --- |
| GET | `/api/collection-groups/{groupId}/plans` | 无 | 全组计划（含自己）+ 成员昵称 + 条件 + 提供标记 + 「你能补的」蛋 id + 我的进行中条数 |
| POST | `/api/collection-groups/{groupId}/plans` | `{ eggGameIds: number[], note?, start? }` | 新建的计划、跳过数、已完成跳过数（`start = true` 全部落进行中） |
| POST | `/api/collection-groups/{groupId}/plans/{planId}/start` | 无 | 计划；想收 → 进行中（不设数量上限），进行中幂等 |
| POST | `/api/collection-groups/{groupId}/plans/{planId}/complete` | 无 | 计划（想收可直接完成；已完成幂等） |
| DELETE | `/api/collection-groups/{groupId}/plans/{planId}` | 无 | 空对象（连带清 `plan_offers`） |
| PUT | `/api/collection-groups/{groupId}/plans/{planId}/offers/me` | `{ note? }` | 「我能提供」标记 / 改备注（upsert） |
| DELETE | `/api/collection-groups/{groupId}/plans/{planId}/offers/me` | 无 | 空对象（撤回标记） |
| POST | `/api/collection-groups/{groupId}/demands/{eggGameId}/placement` | 需求四元组 + `accountKey?` | 需求（`placedAt` 非空；账号标识只落库不返回） |

自动完成：需求结单接口成功后，服务端用 `shouldAutoCompletePlan` 判断「这颗蛋的需求全部结单」，
是则把对应计划置为已完成；中途撤回不产生归档，所以不会误判。

## 9. 历史结单数据红线（硬性要求，2026-11-08）

### ① 这一轨改了几张表

| 表 | 变更 | 说明 |
| --- | --- | --- |
| `collection_group_demands` | **只加两列**（`placed_at`、`placed_by_account_key`，都可空） | 不删行、不改已有列、不改主键、不改唯一约束 |
| `collection_plans` | 新表 | 计划本身，外键只指向 `mother_group_members` |
| `plan_offers` | 新表 | 「我能提供」标记，外键指向 `collection_plans` 与 `mother_group_members` |
| `collection_group_demand_completions` | 未改 | 历史归档表原样保留 |

两个迁移都是「加可空列 / `CREATE TABLE IF NOT EXISTS`」，没有回填、没有重建表，
可以在已有大量历史数据的库上直接执行；`placed_at` 迁移只跑一次（`repeat: 1`，重复执行报 `duplicate column` 属预期）。

### ② 有没有任何一处会删除或改写历史需求行

逐条结论：

1. 删除计划：只 `DELETE FROM collection_plans`，`plan_offers` 由外键级联；
   **不触碰** `collection_group_demands` 与 `collection_group_demand_completions`。
2. 撤回「我能提供」：只删 `plan_offers` 自己那一行。
3. 退出 / 被移出小组：沿用改动前的清理（只删该成员的进行中需求与成员行），
   历史归档表不动；计划与提供标记随成员外键级联清除。
4. 需求结单：仍是「插入归档表 + 删除进行中行」的搬家，与改动前一致；
   新增的自动完成只更新 `collection_plans.status`，不碰需求行。
5. 需求接口返回：原有字段原样保留，只是多了一个可空 `placedAt`；
   `placed_by_account_key` 不进入任何响应，旧客户端不受影响。

### ③ 用什么用例证明

接口用例（`tools/test/collection-groups-api.test.mjs`）：

- `回归：计划的增删改与退出小组都不影响历史结单数据与旧接口结构`
  - 先造 2 条历史结单，记录 `completedCounts` 与 `myRecentCompleted`；
  - 再创建 / 开始 / 完成计划、被别人标记、删除计划；
  - 断言 `completedCounts` 与归档列表逐字段不变；
  - 断言旧字段（`eggGameId / nature / gender / body / voice / status / claimerAccountId / version / createdAt / updatedAt` 等）全部存在；
  - 最后让需求方退出小组，归档仍然是 2 条，计划方的计划仍在。
- 迁移门禁：`node tools/test/verify-mother-groups-schema.mjs`（新迁移已登记，只跑一次标记为 `repeat: 1`）。

真实输出见本轮交付汇报。
