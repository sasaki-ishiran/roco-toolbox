## 1. 逐条复盘

### 1. 迁移没跑就上线，需求查询全部报错、新页面 500（P0）

**现象**：上线后打开小组相关页面，需求列表报 `no such column`（缺列），收集计划新页面因缺表直接白屏 / 500，用户看到的是「功能整个坏了」。

**根因**：断在「定义」和「线上库」之间。`collection_plans` / `plan_offers` 两张表与 `collection_group_demands` 的两个可空列（`placed_at`、`placed_by_account_key`）只写进了 `functions/schema.sql` 和迁移文件，远端 D1 从未执行。而 `deploy:test` 只做 `verify + build + deploy`（`package.json:23`），既不跑迁移，也不校验远端 schema。

**当时的处理**：补执行两个迁移（`functions/migrations/2026-11-08-collection-plans.sql`、`2026-11-08-collection-demand-placed-at.sql`），页面恢复；同时把新表登记进 schema 校验脚本的迁移清单（`eb43ae9`）。

**下次怎么避免**：把「新增表 / 新增列」当成发布前置条件，而不是发布后的补丁。发布顺序固定为：先迁移 → 再核对远端 → 再部署 → 最后冒烟。任何「远端状态我这边看不到」都不构成跳过理由，至少要留一条只读校验命令。

**已经 / 应该沉淀成**：
- 已有：`tools/test/verify-mother-groups-schema.mjs` 会比对 `schema.sql` 区块与迁移文件（但文件头明确写了「不连接远端、不读线上库」，见 `:4-6`）。
- 已有但没变成闸门：2026-11-01 的验收文档其实已经记过同类风险「远端是否已跑无法离线验证，需你确认」（`docs/code-review/2026-11-01-R2/ACCEPTANCE-2026-11-01.md:26`），但没有落成命令，所以今天又踩一遍。
- 应该沉淀：`deploy:test` / `deploy:prod` 前置一条远端 schema 比对（见 §2-G1）。

### 2. 「添加想收」按设计该做多选弹层，实际做成了跳到旧「全部缺口」页

**现象**：点「添加想收」，页面跳到了旧的「全部缺口」页；那页上唯一的动作是「发需求」，按钮名字和实际行为对不上。用户想「先攒几条想收的蛋」，结果被要求当场发需求。

**根因**：断在「设计文档 → 实现」这一层。`docs/收集计划-细化方案-2026-11-08.md` §2 明确写了两件事：一是复用发需求弹层、只保留蛋网格多选；二是批量导入不弹卡直接落库。实现时把「想收」错误地等同于「全部缺口」，于是复用了旧页面入口，而不是新做选蛋弹层。

**当时的处理**：`087434f` 改成手动多选弹层（`DemandPublishSheet` 增加 `wish` 模式，见 `src/ui/DemandPublishSheet.tsx:67`、`:207`），「全部缺口」降级为独立入口，只做盘货 + 发需求（`src/ui/plan/MyCollectionView.tsx:29`、`:196`）。

**下次怎么避免**：实现前先把设计文档里的「主按钮 / 落点 / 动作」抄成一张三列表，逐项对代码；只要出现「跳页」而文档写的是「弹层」，就停下来确认。

**已经 / 应该沉淀成**：按钮标签与动作一致性的组件测试（见 §2-G3）；产品交互规范补一句「同一动作不能在两个入口给出不同结果」。

### 5. 方向性误判：用户说「添加想收」难用，我给的是「系统推荐 8 条 + 一键全部加入」

**现象**：用户反馈「添加想收不好用」，我给出的方案是让系统按规则先挑 8 条、再让用户一键全部加入。用户反问：「你计算出的就是用户想要的吗？」

**根因**：断在「回查历史结论」这一步。项目在 2026-10-03 已经明确否定过「系统代挑」（`docs/superpowers/plans/2026-10-03-呈现层精简与母本待办.md:67`：「原先只由系统在建议里代挑一条；改成用户自己挑目标并跟踪进度」）；2026-10-31 又定过「先由用户定口径，系统再按口径算」（`docs/产品交互规范.md:279-283`）。两条都指向同一个原则：**选择权在用户，系统只做按口径计算**。我的方案正好逆着这两条。

**当时的处理**：撤回「系统代挑」方案，改成手动多选弹层；「按你的口径算的全部缺口」只作为弹层里的一个快捷按钮，由用户自己点。

**下次怎么避免**：用户说「不好用」时，先做一次历史结论检索（`docs/**` 搜关键词 + 拍板日期），把相关结论摆出来再出方案；方案里必须写一句「这不违反 X 结论，因为……」。凡是「系统替用户决定内容」的方案，默认先假设它违反本项目原则。

**已经 / 应该沉淀成**：流程条款——「方案评审前必须回查原始需求与历史拍板」（见 §3-1）。

### 6. 采集器上传 426，先查错了端

**现象**：上传采集包返回 HTTP 426，我一开始去查 PC 端 exe 的采集逻辑，查了半天没结论。用户纠正原话：「不是这个，是采集器，刚放进去的安卓采集器」。

**根因**：断在「先定位端」。426 来自蛋神助手云端采集服务，它从 1.3.0 / code 63 起拒绝旧版身份（`android-shell/app/src/main/java/com/localdatatool/toolbox/capture/CaptureUploader.java:26-31`），而我们请求头仍是旧版本号。跟 PC 端 exe 无关。

**当时的处理**：把上传身份常量集中到 `CaptureUploader` 一处并抬到当前公开版本（`:38-40`，`UPSTREAM_VERSION` / `UPSTREAM_VERSION_CODE`），请求头统一从这里取（`:251-254`）。

**下次怎么避免**：拿到错误码先问三件事——哪个端、哪个版本、哪个服务返回的。三个都没钉死之前不翻代码。

**已经 / 应该沉淀成**：采集器身份常量单点化（已做）+ 一条单测断言「请求头版本 = 常量」（见 §2-G8），避免下次再散落。

### 7. 两路同时改 `android-shell/`：编译不过 + 根目录安装包被覆盖

**现象**：一路做悬浮球与采集保活，一路做悬浮面板。结果面板侧在 `BattleOverlayController` 里加了一个未初始化字段，整个仓库编译不过；两路还共用过同一个构建目录，根目录的 1.2.5 安装包被覆盖过一次。

**根因**：断在并行边界。两个会话都认为自己「只改一点点」，但目录是同一份、构建输出也是同一份，没有 ownership、没有隔离的产物目录（版本号仍停在 `versionName "1.2.5"` / `versionCode 16`，`android-shell/app/build.gradle:23-24`），覆盖后也无法从文件名区分是谁打的包。

**当时的处理**：补齐字段初始化恢复编译；被覆盖的安装包只能重新打包恢复；随后把手机悬浮窗方案与面板规格冻结成文档（`0cdec97`），让两路以文档为唯一依据。

**下次怎么避免**：同一目录同一时间只允许一个会话有写权限；并行只允许发生在不同目录。构建产物必须带版本 + 会话标识，禁止共用根目录输出。

**已经 / 应该沉淀成**：目录级互斥规则（见 §3-3）+ 构建产物隔离与版本校验（见 §2-G7）。

### 8. 「采集不刷新」的真实成因：页面不可见，WebView 把定时器节流了

**现象**：进游戏后悬浮球和计数长时间不动，看起来像采集链路断了。

**根因**：断在运行环境，不在业务代码。用户切到游戏后工具箱页面不可见，WebView 会把 `setTimeout` / `setInterval` 节流到分钟级甚至暂停，网页侧的轮询自然停摆。一开始把它当成采集链路问题排查，方向错了。

**当时的处理**：原生每秒唤醒网页一次（`android-shell/app/src/main/java/com/localdatatool/toolbox/MainActivity.java:110-125` 的 `liveTick`，`evaluateJavascript` 不受页面定时器节流影响）；网页侧补 15 秒卡死看门狗，一轮解析超时就被后台心跳中止并重开（`src/collector/useCaptureProgress.ts:14-15`、`:223`），同时给后台轮询单独开了 `background` 开关（`:52-57`）。

**下次怎么避免**：遇到「定时不动」先区分「数据没来」还是「定时器没跑」；能采集到运行时证据（心跳日志 / 前后台状态）就先采证，再改代码。

**已经 / 应该沉淀成**：代码注释已写清原因（上面两处）；建议在采集相关排查清单里固定第一条：「先确认页面是否可见 / 定时器是否被节流」。

### 9. 五步进度的语义硬伤：有一段永远不亮

**现象**：把点阵改成 5 段细条后才发现，服务端的 `progressStep` 永远不会等于 3，5 段里有一段永远不亮；而且同一个计划，发布人和认领人对「已经走到哪一步」的理解并不一致。

**根因**：断在「状态机 → 视觉」的映射。原实现把「已上窝」直接合并成「待我确认」（第 4 步），第 3 步没有任何数据组合能产生，UI 却按 5 段画。

**当时的处理**：`e369510` 先让卡面 5 段与详情五步一一对应；`eb43ae9` 改成按查看者区分——发布人看到第 4 步「待我确认」，认领人看到第 3 步「已上窝」（`src/shared/collectionPlans.ts:146-167`，关键分支在 `:159-162`）。

**下次怎么避免**：改进度类 UI 前，先把「每个 step 由什么数据产生」列成表，逐个确认可达；不可达的 step 要么删掉，要么补数据来源。

**已经 / 应该沉淀成**：状态机可达性单测（见 §2-G9）；规范里补一句「进度段数必须等于状态机里可达的档位数」。

## 3. 流程层面的教训

### 3-1 什么时候必须先回查原始需求原文

- 用户说「不好用 / 不对劲」时：**先搜 `docs/**` 与历史拍板日期，再出方案**。今天坑 5 就是没查，逆着 10-03「不要系统代挑」和 10-31「先由用户定口径」两条结论走。
- 方案里必须能回答一句：「这不违反 X 结论，因为……」。答不出来就先问用户。
- 涉及「系统替用户做选择」的方案，默认高风险，先假设它违反本项目原则。

### 3-2 什么时候必须先跑迁移再发布

- 只要这次改动**新增了表或列**，发布顺序强制固定：迁移 → 核对远端 → 部署 → 冒烟。没有例外。
- 「远端我看不到」不是跳过理由：至少留一条只读校验命令（`pragma_table_info` / `sqlite_master`），并把它写进发布清单。
- 迁移是否能重复执行要显式标注（`repeat: 1` 表示只能跑一次），并在发布记录里写明「已执行 / 未执行」。

### 3-3 并行改同一目录怎么划边界

- **目录级 ownership**：同一时间，一个目录只允许一个会话有写权限。`android-shell/` 这种原生目录尤其不能两路并行。
- 并行只发生在**不同目录**（例如今天 A 轨埋点、B 轨文案、C 轨收集计划是可以并行的，因为它们落在不同文件）。
- 共用构建目录必须禁止：产物按「版本 + 会话」隔离，根目录不再直接放安装包，避免互相覆盖后无法追溯。
- 合并前各跑一次**整体编译**，而不是只跑自己文件的测试——今天面板侧一个未初始化字段就让全仓编译不过。

### 3-4 先定位层级，再动手

- 拿到现象先钉死三件事：**哪个端（网页 / 安卓壳 / PC exe / 云端）、哪个版本、哪个服务返回**。坑 6 的 426 就是端没钉死。
- 「没刷新 / 没更新」这类现象先分成「数据没来」和「定时器没跑」两类（坑 8），能采运行时证据就先采证。
- 结论必须落到具体交付物：「X 阻塞 Y」。坑 10 的「收集计划阻塞打包」写不出 Y，所以它本来就是错的。

### 3-5 新 UI 仍然先审后做

- 今天卡片方案被否一次（单列 → 两列三方案 A/B/C），再次验证 `AGENTS.md` 的「新增 UI 必须先审核再实现」是对的。
- 审核材料要给 375 / 390 对照 + 可交互 HTML，而不是文字描述；用户挑完方案再落代码。

## 4. 下一次同类任务开工前的 5 条检查

1. **有没有新增表或新增列？** 有就把迁移放到第一件事，并写一条能核对远端的只读命令。
2. **这个按钮点下去，标签说的和实际做的是不是同一件事？** 尤其「添加 / 发起 / 导入 / 发布」这四个词。
3. **这一屏里有没有第二套卡型、第二个旧入口？** 旧页面是不是还活着、还在被渲染？
4. **用户说的现象在哪个端、哪个版本？** 三件事没钉死之前不翻代码、不改代码。
5. **我这次的方案，和项目里已拍板的历史结论冲突吗？** 先搜 `docs/**` 再出方案，并在方案里写明不冲突的理由。
