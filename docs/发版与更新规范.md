# 发版与更新规范（单一来源）

> 本文是「网页发版 / 安装包分发 / 更新检测 / 转正 / 回滚 / 交接卡」的唯一口径。
> 与本文冲突的旧习惯一律作废；改流程先改本文，再改脚本。

## 一页速查

**日常更新**

1. 改代码：功能与修复走内测分支；**要随版本发出去的网页改动，先合进 `release`**（见 §4.2）→
2. 打内测包（独立 App、默认测试站、读内测清单）→ 3. 内测 App 验收 →
4. **提交**：把要发布的改动提交到 `release`（壳版本号一并提交），构建前完成，见 §4.2 →
5. 用**正式参数重新构建**（禁止复制内测包）→ 6. 在一个发布窗内依次发 **包 → 清单 → 网页**（见 §4.1）→
7. 发完复核 → 8. 留交接卡。

```bash
# 6. 三件套（顺序不能反，且必须同一批做完）
#    a) 包：上传版本化 APK + 覆盖 latest.apk
#    b) 清单：public/android/version.json 与 version-18.json 抬到新版本
#    c) 网页：只走脚本，不手敲 wrangler
node scripts/deploy-web.mjs --branch main --approve-production
```

**两条硬流程（写进流程，不是建议）**

1. **包、清单、网页同一次发布窗内做完**，顺序固定「版本化包 → `latest.apk` → 两份主站清单 → 网页」；
   不允许先换包隔一阵再发清单，也不允许先发清单后换包。窗口期的具体后果见 §4.1。
2. **要随版本发出去的网页改动，发版前必须已在 `release` 上**并被核对过；
   发现改动还在功能分支上就停下来先合，不许构建时临时摘取。收集计划只走内测、永远不进正式线，见 §4.2。

> 内测独立 App（独立 `applicationId`）目前**尚未落地**，现状是同一包名 + 内测构建参数，见 §9 待办。
> 在它落地前，内测包不得让非内部人员安装。

**回滚**：网页 + `latest.apk` + 两份清单**三件一起回**。
只回网页等于没回：清单还指向新包、下载站还在发新包，用户照样升级到出问题的版本，只是网页看起来旧了。

**出问题先查这五项**

1. 三份清单（主站 `version-18.json`、主站 `version.json`、下载站 `version.json`）版本号与 `apkUrl` 是否一致；
2. 包内默认站（`BuildConfig.DEFAULT_SERVER_URL` / dex 里的站点地址）；
3. 签名证书 SHA-256 是否与现网一致；
4. 客户端 `skippedVersionCode` 是否把目标版本静默跳过；
5. 静默更新检查是否失败被吞（无日志、无重试、只在启动后跑一次）。

细节分别见 §3 / §7 / §11。

**动手门槛（硬约束）**：打包、删除/覆盖产物、部署发版、新增或改版界面这四类动作，
**没有当轮明确指令一律不做**。允许做的事也要先说明打算做什么、产物落在哪；已产出的文件不自行删除，只报告等指令。
完整条文见 `AGENTS.md` 的「先问再做：四类动作的硬门槛」，两处口径一致，改一处必须同步改另一处。

## 铁律（先读）

**身份按 origin 存在浏览器本地存储里。改默认站点 = 一次数据迁移。**

用户的令牌、accountId、云同步版本都存在当前站点 origin 的 localStorage。换一个 origin 打开，
就是另一套 localStorage——服务端 D1 里的账号还在，但设备上看不到。因此任何「默认站改成 X」的改动
都必须先按迁移评估：影响人群、找回路径、是否需要救援逻辑、是否需要恢复码补偿，**不能当成改一个常量**。

四条硬约束：

1. **两个包必须不同 `applicationName` / `packageId`**：内测 App 独立安装、天然隔离数据，不覆盖正式包。
2. **正式包不可改站点**：不提供切服入口、不提供改地址面板，默认站只认正式站。
3. **打包期断言**：构建必须打印并校验通道、默认站、清单；正式包不得出现内测清单，内测包必须含测试站与内测清单。
4. **发版期断言**：`deploy-web.mjs` 必须校验两份正式清单存在、可解析、内容一致、`apkUrl` 指向正式包，
   且正式 bundle 不含内测批次文案（如「收集计划」）。

## 1. 通道模型

一个包只属于一个通道，由构建参数决定，不允许一个包装两个身份。

| | 正式通道 `production` | 内测通道 `internal` |
|---|---|---|
| 网页 | `https://roco-toolbox.pages.dev` | `https://test.roco-toolbox.pages.dev` |
| 包默认站 | `https://roco-toolbox.pages.dev` | `https://test.roco-toolbox.pages.dev` |
| 更新清单（主） | 主站 `/android/version-18.json`（可信，可强更） | 下载站固定路径 `/internal/version.json`（可用 `-PinternalManifestUrl` 覆盖） |
| 更新清单（兜底） | 主站 `/android/version.json`、下载站 `/android/version.json`（只提示，不强更） | 无公开兜底 |
| 安装包 | 下载站 `android/roco-toolbox-latest.apk`（固定名） | 独立内测位置，只用版本化文件 |
| 面向 | 所有用户 | 内部人员 |
| 构建参数 | 默认（不传 `-PtestBuild`） | `-PtestBuild=true`（内测清单默认固定，可用 `-PinternalManifestUrl` 覆盖） |

硬规则：

- 构建必须打印并断言：`[通道校验] channel=… version=… default=… manifest=…`。
- 断言内容：生成的 `BuildConfig.DEFAULT_SERVER_URL` 必须等于通道默认站；正式包不得出现测试站地址或内测清单；内测包必须有测试站地址和独立清单。
- **转正 = 同一份代码用正式参数重新构建**；禁止把内测包复制进正式清单，禁止改个 `apkUrl` 就把内测包当正式包。
- 内测清单固定在 `https://roco-toolbox-downloads.pages.dev/internal/version.json`（可用 `-PinternalManifestUrl` 覆盖）。**它不作为安全边界**：只是一个不放进公开入口的固定路径，公开包不读取它，也不会在公开页面里链接它。
- 内测包不改 `latest.apk`、不改 `public/android/version.json` 与 `version-18.json`。
- 正式站部署仍然只走 `scripts/deploy-web.mjs`，且必须用户明确放量 + `--approve-production`。

## 2. 两个通道各自的产物

### 正式通道

1. 网页：`roco-toolbox` 项目的 Production 部署。内容来自 `release` 分支的 `dist`
   （部署时 `--branch main` 只是 Pages 通道标签，见 §4「放量口径」）。
2. 清单：`public/android/version.json` + `public/android/version-18.json`，两份内容必须完全一致（版本号、`apkUrl` 都一致），随 `dist/` 一起部署。
3. 安装包：下载站 `roco-toolbox-downloads.pages.dev/android/roco-toolbox-latest.apk`（固定名）+ 版本化文件（保留，便于回滚与用户自装）。
4. 版本号：`versionCode` 单调递增，`versionName` 与两份清单一致（构建期 `verifyShellInvariants` 会拦）。

### 内测通道

1. 网页：同项目 `test` 分支部署（`test.roco-toolbox.pages.dev`）。
2. 清单：固定在 `https://roco-toolbox-downloads.pages.dev/internal/version.json`（可用 `-PinternalManifestUrl` 覆盖），不放在公开 `public/android/` 里，公开包不读取。
3. 安装包：版本化文件（如 `roco-toolbox-1.5.3-internal.apk`），不占用固定名。
4. `-PtestOnlyBuild=true` 仅用于「不更新线上清单的单人验证包」，它和通道参数是两件事：
   - `testBuild` 决定默认站与清单；
   - `testOnlyBuild` 只跳过「versionName 必须与正式清单一致」。

## 3. 更新检测链路（与包默认站无关）

已核实：更新地址写死在构建配置里（`build.gradle` → `BuildConfig`），**不读 `ServerConfig.baseUrl()`**。改默认站不会改变更新检测、下载地址或更新模式。

正式通道读取顺序（`UpdateController`）：

1. 主站 `/android/version-18.json` —— 可信，`minSupportedVersionCode` 生效，可触发全屏强更；
2. 主站 `/android/version.json` —— 只提示，不强更；
3. 下载站 `/android/version.json` —— 只提示，不强更。

内测通道：只读 `BuildConfig.MANIFEST_URL`（内测清单），不混入任何公开清单，避免内测机被公开版本顶掉。

判断逻辑：

- `manifest.versionCode > 当前 versionCode` 才提示；
- `minSupportedVersionCode > 0 && 当前 versionCode < 它` 才强制更新；当前三份清单都是 `0`，不锁人；
- 「稍后」记住 `skippedVersionCode`，只跳过该版本；
- 下载地址只用清单里的 `apkUrl`，客户端不写死 APK 地址。

已知历史遗留（不要用）：

- 正式站 `/android/roco-toolbox-latest.apk` 还挂着一个 **1.2.6（versionCode 17）** 的旧包，是 7 天边缘缓存残留（`s-maxage=604800`），当前清单不引用它。排查更新问题时不要把它当成「正式包」。

## 4. 转正流程

1. 固定内测网页部署 commit；确认内测清单与内测包版本一致。
2. **先提交，再构建**：把本次要发的改动（网页、清单、壳版本号）提交到 `release` 并推送；
   构建前核对工作区干净。部署来源记录的 commit 必须就是发布 commit，回滚才找得回来。
3. **用同一份代码、正式参数重新构建**正式包：不传 `-PtestBuild`，确认构建输出 `channel=production` 且 `default=https://roco-toolbox.pages.dev`。
4. 校验正式包：包名、签名与线上一致，`versionCode` 单调递增，默认站为正式站（可反汇编 dex 复核）。
5. 上传正式包到下载站；先传版本化文件，再替换固定名 `roco-toolbox-latest.apk`；回读字节数与 SHA-256。
6. 更新 `public/android/version.json` 与 `version-18.json`（同一版本号、同一 `apkUrl`）。
7. `npm run build`，然后跑演练：
   `node scripts/deploy-web.mjs --branch main --approve-production --dry-run`
   必须看到 bundle 断言 + 正式清单断言全部通过。
8. 用户明确放量后执行正式部署，记录 Cloudflare 部署 ID。
9. 填写交接卡（见 §6）。

### 放量口径：正式网页不含收集计划

- 正式网页由 `release` 分支（当前 `88bce8d`）的 `dist` 产出。部署命令里的
  `--branch main` 只是 Cloudflare Pages 的通道标签（决定进正式域名还是预览域名），**不代表 git 分支**。
- 收集计划（发布计划 / 组内认领 / 组内广场 / 需求中心改版）继续留在
  `test` 分支，只走内测通道（`--branch test` → `test.roco-toolbox.pages.dev`）。
- 为什么要把这条写成放量口径：收集计划还在内测验收阶段，而正式站是用户正在使用的主入口。
  一旦把含收集计划的 dist 发上去，未验收功能会直接扩散到所有用户；而且按 §5，
  回滚必须网页 + 清单 + 包三件一起回，代价远高于发版前多跑一次断言。
- `scripts/deploy-web.mjs` 的「正式 bundle 不含『收集计划』」断言**保持不变**。它不依赖人记，
  任何一次 `--branch main` 部署只要 bundle 里出现这四个字就中止。以后有新内测批次功能，
  照这个做法在脚本里补一条对应断言，而不是靠口头约定。

### 4.1 包、清单、网页必须同一次发布完成（硬流程）

**不允许**把一次发版拆成两段：先换下载站 `latest.apk`、过一阵再部署主站清单；也**不允许**反过来先发清单、后换包。
一次发版必须在一个发布窗内按下面的顺序做完，中途不隔夜、不「先上一半看看」：

1. 上传**版本化**包（`roco-toolbox-<版本>.apk`），回读字节数与 SHA-256；
2. 覆盖下载站固定名 `roco-toolbox-latest.apk`，回读 SHA-256，必须与第 1 步一致；
3. 同一批改 `public/android/version.json` 与 `public/android/version-18.json`（`versionCode` / `versionName` / `apkUrl` 三处一致）；
4. 部署网页（`node scripts/deploy-web.mjs --branch main --approve-production`）；
5. 立刻复核：三份清单版本号与 `apkUrl` 一致、固定名包的 SHA-256 与交接卡一致、网页下载入口拿到的是同一份包。

为什么必须一批做完：**版本判断只读主站清单，下载只认 `apkUrl` / 固定名**，这是两条独立链路，
中间任何一段错位，用户装到的包和客户端以为的版本就是两回事：

- **包先换、清单后发**：清单还写着旧版本，老客户端判断不出「有新版本」，更新链断掉、没人收到提醒；
  但网页下载入口和固定名已经是新包，新装 / 重装用户装到的是新版，设置里显示的版本号又和清单对不上，
  表现为「我装的明明是新的，却还提示我更新」或「版本号和下载页不一致」。
- **清单先发、包后换**：所有在线客户端都弹更新提示，点下载拿到的还是旧包，装完继续提示，形成死循环；
  这种提示打的是全部用户，不只是新装用户，影响面比上一种更大。
- 窗口期内若要回滚：清单回到旧版本、固定名却还是新包，等于没回（回滚必须三件一起回，见 §5）。

所以判断标准不是「过一会儿补上」，而是**要么整批不发，要么一次发完**。
发布窗内任一件失败，按 §5 把网页 + 清单 + 包一起退回去，不许只退其中一件。

### 4.2 网页改动必须先合进正式线（硬流程）

正式线的唯一来源是 `release` 分支：正式网页的 `dist` 由它构建，
部署命令里的 `--branch main` 只是 Cloudflare Pages 的通道标签，**不代表 git 分支**。

- 任何要随这次版本发出去的网页改动（新功能、修复、文案、依赖与构建配置都算）**发版前必须已合进
  `release` 并推送**。构建 `dist` 之前先核对：`git log --oneline release` 里有这些提交，
  且工作区干净（`git status` 无未提交改动）。
- **不允许**到构建时才发现改动还在功能分支上，再临时 cherry-pick、手工拷文件，或直接拿功能分支构建后打 `main` 标签。
  那样发出去的网页和分支上被核对的代码不是同一份，回滚与复盘都没有参照。
- 反过来也要看：功能分支上的内容不能被顺手带进正式线。收集计划（发布计划 / 组内认领 / 组内广场 / 需求中心改版）
  永远不进正式线，只走 `test` → 内测站（`--branch test`）；
  `deploy-web.mjs` 的「正式 bundle 不含『收集计划』」断言是最后一道机械拦截，不放宽、不绕过。

为什么写成硬流程：这次发版暴露的漏点就在这一类——**修复类网页改动**容易被当成小事，在内测分支上验完就算完，
到构建正式 `dist` 时才发现正式线里没有这段代码，发出去的版本等于没修；临时摘取又会把没被核对过的代码带进正式包。

> 1.5.6（2026-11-15）属于**先发后补**的特殊情况：包、清单、网页先发，改动在发布后才补提交（`9fbfec0`），
> 因此该次部署来源显示的是旧 commit `736e181`。后续发版一律按本节「先提交、再构建」，不再允许这个顺序。

## 5. 回滚流程

回滚必须 **网页 + 清单 + 包** 三件一起回，不允许只回网页：

1. 选定回滚目标：上一个正式网页部署 ID + 对应的清单版本 + 对应的 APK。
2. 把两份正式清单改回目标版本，`apkUrl` 指向目标 APK（固定名或版本化文件）。
3. 把下载站固定名切回目标 APK，或把 `apkUrl` 固定指向目标版本化文件。
4. 网页回滚到目标部署（Cloudflare rollback 或重新部署目标 commit 的 `dist`）。
5. 复核三处版本一致（网页、清单、APK），再填交接卡。
6. 只回网页会造成「新清单 + 新包 + 旧网页」，客户端会继续被提示更新，问题不会消失。

## 6. 每次发版必须产出的交接卡

```md
## 发版交接卡

- 通道：production / internal
- 版本：1.5.3 (versionCode 37)
- 构建参数：-PtestBuild=false / -PtestBuild=true（内测清单默认固定）
- APK：roco-toolbox-1.5.3.apk
  - 字节数：…
  - SHA-256：…
- 清单：https://…/android/version-18.json
  - versionCode：37
  - apkUrl：https://roco-toolbox-downloads.pages.dev/android/roco-toolbox-latest.apk
- 网页部署：分支 main / commit … / 部署 ID …
- 正式版内容条目（从提交列表生成）：
  - …
  - …
- 验证记录：冷启动 / 覆盖升级 / 更新检测 / 回滚演练
- 回滚目标：上一个部署 ID …，上一版 APK …
```

交接卡至少包含：通道、版本、包 SHA-256、清单地址、网页部署 ID、正式版内容条目、回滚目标。

## 7. 机械校验清单

| 校验 | 位置 | 触发 | 失败后果 |
|---|---|---|---|
| 版本清单一致 / 壳不变量 | `android-shell/app/build.gradle` 的 `verifyShellInvariants` | `preBuild` | 构建失败 |
| 通道 / 默认站 / 清单地址 | `verifyChannelBuildConfig`（挂在 `generate*BuildConfig` 之后） | 任意构建 | 构建失败 |
| 正式 bundle 不含内测文案 | `scripts/deploy-web.mjs` | 每次发版 | 中止部署 |
| 正式清单存在、可解析、版本一致、只指向正式包 | `scripts/deploy-web.mjs`（仅 `--branch main`） | 每次发正式 | 中止部署 |

自查命令：

```powershell
# 正式通道：应打印 channel=production / default=https://roco-toolbox.pages.dev
.\gradlew.bat verifyChannelBuildConfig -PtestOnlyBuild=true

# 内测通道：应打印 channel=internal / default=https://test.roco-toolbox.pages.dev
# 清单固定为 https://roco-toolbox-downloads.pages.dev/internal/version.json
.\gradlew.bat verifyChannelBuildConfig -PtestBuild=true -PtestOnlyBuild=true

# 网页发版演练（不部署）
node scripts/deploy-web.mjs --branch main --approve-production --dry-run
```

> Windows 构建提示：在含中文的路径下，CMake / ninja 可能报

## 11. 1.5.4 身份救援（已实现，待真机验证）

背景：1.3.8 ~ 1.5.2 的公开包默认打开测试站，用户在这段时间建立的令牌与 accountId 存在测试站
origin 的 localStorage；1.5.3 改回正式站后，这些身份「看不见」，但 D1 里的账号与令牌仍然有效。

为什么不能用 deviceId 自动找回：deviceId 由网页 `crypto.randomUUID()` 生成，只存在
localStorage 的 `roco.deviceId`，按 origin 隔离；换站就是新 id，服务端 `devices` 映射匹配不回旧账号。

实现（`IdentityRescue.java`，仅正式包执行）：

- 条件：`BuildConfig.CHANNEL == production`、当前打开正式站、正式站没有 `roco.deviceToken`、
  本次安装没救援过（`roco_rescue.done`）。
- 动作：隐藏 WebView 依次打开正式站 / 测试站的 `/android/version.json`（同源轻量文档），
  读 `roco.deviceToken` / `roco.accountId` / `roco.syncVersion`；测试站有 token 就写进正式站 origin，
  再正常加载；测试站也没有就静默跳过；正式站已有身份绝不覆盖。
- 超时 2.5 秒放弃且不落标记，下次启动可重试；任何异常都不阻塞启动。
- 内测包（`CHANNEL == internal`）不执行这段逻辑。

> 注意：正式包 dex 现在**有意包含测试站地址**（救援要打开它）。之前的
> 「正式包 dex 不含测试站地址」断言需要改成「只允许出现在 IdentityRescue 相关字符串里」。

真机验证三种情况：

1. **正式站已有身份**：装 1.5.3 并登录后覆盖装 1.5.4 → 打开直接是已登录，页面不闪、不重登，
   `roco_rescue.done` 被置位，身份未被改写。
2. **正式站空、测试站有 token**：先用 1.5.2（默认测试站）建号/建组，再覆盖装 1.5.4 →
   打开直接显示已登录，小组与云端版本回来，无需输恢复码（最多多等约 0.2~2.5 秒）。
3. **两边都空**：全新安装 1.5.4 → 正常打开，显示「还没有工具箱身份」，无白屏、无报错。

同一台设备想重复验证，需要卸载重装（会同时清掉标记与身份）；救援每次安装只跑一次。
