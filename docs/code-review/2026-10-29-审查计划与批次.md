## 4. 分级与输出格式（所有批次统一）

### 4.1 分级

- **高风险**：逻辑错误、实现与需求不符、并发/边界/异常处理缺陷、明显性能问题（N+1、循环内 IO、复杂度失控）、数据正确性问题（精度、时区、编码、事务、幂等）、安全漏洞（注入、越权、敏感信息泄露）
- **中风险**：违反第 3 节明确规范、明显过度复杂、职责耦合、重复逻辑、错误处理不一致、可测试性差
- **低风险**：死代码、无用导入、命名/注释瑕疵、格式问题
- **不确定**：证据不足或依赖业务语义；必须标置信度 + 需要谁确认，不得自行假设

### 4.2 条目编号

`B{批次号}-{H|M|L|U}{两位序号}`，例如 `B3-H01`、`B5-M04`、`B9-U02`。
编号在**合并报告时不再改动**，修复提交的 commit message 直接引用该编号。

### 4.3 每条必须包含

等级 / 文件:行号 / 一句话标题 / 问题描述（含代码片段或调用链）/ 影响面（什么操作触发、用户看到什么）/ 修复建议（具体到怎么改）/ 置信度。缺任一项视为不合格。

### 4.4 每批报告文件

`docs/code-review/2026-10-29/B{n}-{短名}.md`，末尾附：本批问题数量统计、本批最该先修的 1~3 条、范围外备注（看到但不属于本批的，只记录不展开）。
