## B2-H01 母本摘要的产线依赖构建时的目标模式，但摘要不记录、可比性也不校验模式（已修复 `e93c778`，方案 A）

- **等级**：高
- **文件:行号**：[motherResource.ts:105-111](file:///d:/desk/洛克工具箱/src/domain/motherResource.ts#L105-L111)、
  [shared/motherGroups.ts:122-127](file:///d:/desk/洛克工具箱/src/shared/motherGroups.ts#L122-L127)、
  [motherSharing.ts:36-46](file:///d:/desk/洛克工具箱/src/domain/motherSharing.ts#L36-L46)、
  使用处 [MotherGroupResources.tsx:255-270](file:///d:/desk/洛克工具箱/src/ui/MotherGroupResources.tsx#L255-L270)
- **问题描述**：
  `buildProductionLines` 的 `mode` 决定档位门槛（`perfect` = `|dB| = 100`，`medal` = `|dB| ≥ 96`），
  所以同一份背包在不同模式下算出的 `lines` 不一样。但：

  - `MotherResourceDraft` / `SharedMotherAccount` 都没有 mode 字段；
  - `isMotherResourceComparable(resource, catalogVersion, criteriaId)` 只比 `criteriaId` + 图鉴版本，
    `criteriaId` 固定是 `all-mothers-v2`，与 mode 无关；
  - 组长切模式时（`GroupTargetEditor.tsx:174-179` 的 `changeMode`）只改组目标，成员已发布的
    `lines` 仍是旧模式算的，却继续被判定为「可比」。

  结果：组内产线口径混用。举例 —— 组从「追满分」切到「追双牌」后，某成员 96~99dB 的配对
  本应算能补，但旧摘要里没有这条线，于是被算成缺口；反向从「追双牌」切到「追满分」时，旧摘要里
  96dB 的「大婉」会被当成 100dB 的满分线，误判成能补。
- **影响面**：小组「我缺的 → 谁能补」「需求中心 → 我能接的」的判定随「最后一次由谁、在什么模式下
  发布」而变；切换目标模式后 UI 只提示「成员需要重新发布」，但资源仍显示「已发布」，成员不会收到
  「需更新」，实际口径不会自动对齐。
- **修复建议（需要业务决策，先别动手）**：
  - 方案 A：把 `mode` 写进 `MotherResourceDraft`（与种公摘要保持一致），纳入
    `isMotherResourceComparable`，并把 `ALL_MOTHERS_CRITERIA_ID` 升到 `all-mothers-v3`，
    切换模式后全员显示「需更新」；
  - 方案 B：`lines` 统一按 `perfect` 存（只记 ±100 的线），medal 模式在查看端自行放宽。
    这能保证不误判「能补」，但会漏掉「只有 96~99dB 配对」的成员（正是 2026-10-28b 要修的漏单）。
  - 两个方案影响面不同（A 要多一次全员重发，B 会重新引入漏单），需要你拍板。
- **置信度**：高（代码路径清楚；触发条件是组长切模式这一常规操作）

## B2-M01 同一份母本摘要由三个入口构建，其中两个入口的 mode 取值与小组不一致（已修复 `e93c778`）

- **等级**：中

  `CollectionGroups`），所以现在只是潜在回归点；一旦恢复该入口就会真实发生。
- **修复建议**：`mode` 改为必传（配合 H01 一起定），或在 `buildMotherResource` 内部从组目标派生，
  不再允许调用方漏传。
- **置信度**：高（调用点可直接看到）；是否为「已废弃入口」需要 B10 一起确认

## B2-M02 摘要生成侧不校验产线上限与请求体大小，超限只能等服务端报错

- **等级**：中（与 B4-M3 同源，这里只从域模型侧提出）
- **文件:行号**：[motherResource.ts:75-160](file:///d:/desk/洛克工具箱/src/domain/motherResource.ts#L75-L160)
  （只校验了 `eggGameIds` 上限，没校验 lines）；上限常量
  [shared/motherGroups.ts:37-38](file:///d:/desk/洛克工具箱/src/shared/motherGroups.ts#L37-L38)、
  [58-61](file:///d:/desk/洛克工具箱/src/shared/motherGroups.ts#L58-L61)
- **问题描述**：服务端校验「单账号 ≤1024 条产线、每条 ≤30 个性格、整包 ≤128KiB」，
  但客户端 `buildMotherResource` 只挡了「单账号 ≤1024 个蛋」。产线是 蛋 × 档位，可以远多于蛋数：
  220 个蛋 × 4 档 ≈ 880 条/账号；按每条 `{"eggGameId":101,"grade":"大婉","natures":["固执",...]}`
  约 60~90 字节估算，**两个账号就可能接近或超过 128KiB**。超限时前端不做预检，用户等到提交后
  才收到 413 / `INVALID_INPUT`，提示与「发布」动作对不上。
- **影响面**：收集度高、多账号的用户发布失败；失败提示里看不到「哪一项超了」。
- **修复建议**：在 `buildMotherResource` 里按 shared 常量做同一套校验（产线条数 / 性格数 / 序列化
  字节数），抛出可读的 `MotherResourceError`（如 `TOO_MANY_LINES` / `PAYLOAD_TOO_LARGE`）；
  上限的具体数值本身要不要调，由 B4 决定。
- **置信度**：中（未实测真实字节数；体量为按现有数据量的估算）
