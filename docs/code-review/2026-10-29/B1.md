## B1-H01 种的公需求「配窝个体」可能挑到不达标的那只（已修复 `7c5aaaa`）

- **等级**：高
- **文件:行号**：[demandCriteria.ts](file:///d:/desk/洛克工具箱/src/domain/demandCriteria.ts#L229-L249)（`pickPet` 230–238）
- **问题描述**：
  `findBreedableSupply` 已经用「蛋 + 性别 + 体型 + 声音 + 性格」筛出了具体那一个合格个体，并把它的
  `gameId` 放进 `motherGameId` / `maleGameId`。但 `findStudBreedableSupply` 随后用 `pickPet()` 按
  **gameId + 性别 + 性格** 重新挑人，丢掉了体型 / 声音条件：

  ```ts
  const candidates = (snapshot?.pets ?? []).filter(
    (pet) => pet.gameId === gameId && pet.gender === gender,
  );
  return (
    candidates.find((pet) => !demand.nature || pet.nature === demand.nature) ??
    candidates[0]
  );
  ```

  同一个图鉴号有多只（母本清单里很常见）时：背包里同时有「大块头 + 固执」和「小不点 + 固执」两只
  火花，`findBreedableSupply` 选的是大块头那只，`pickPet` 却会按 `nature === '固执'` 先命中
  **小不点**那只。函数注释写的是「展示的配对才孵得出来」，实际不一定。
- **影响面**：种公需求的「需求中心 → 点头像看用哪两只配窝」会显示不达标的母本 / 公；用户照着配窝，
  孵出来仍然达不到需求，容易被当成工具算错（这条展示是 2026-10-28b 新加的主路径）。
- **修复建议**：不要按 gameId 反查，直接让 `findBreedableSupply` 把选中的 `OwnedPet` 带出来
  （例如 `DemandSupply` 增加 `motherPet?/malePet?`，或在 `findStudBreedableSupply` 内部就地重算
  「蛋 + 同蛋组公」两段筛选并返回个体），避免二次挑选时丢条件。测试补一例：
  同图鉴号两只母本、一只达标一只不达标，断言返回的是达标那只。
- **置信度**：高（代码路径可直接推导；现有单测只覆盖「两只都达标、性格不同」的情形，测不出来）

## B1-M01 声音匹配在 demandCriteria 里复制了一份，且边界与 petFilters 不一致

- **等级**：中（依据：`petFilters.ts:133-137` 明确写「各筛选器共用这一个函数，避免三处复制逻辑又改漏」）
- **文件:行号**：[demandCriteria.ts:36-43](file:///d:/desk/洛克工具箱/src/domain/demandCriteria.ts#L36-L43)、
  对照 [petFilters.ts:138-151](file:///d:/desk/洛克工具箱/src/domain/petFilters.ts#L138-L151)
- **问题描述**：

  ```ts
  if (voice === '婉转声') return pet.voiceDb >= 96;    // petFilters: >= 96 && <= 100
  if (voice === '粗嗓门') return pet.voiceDb <= -96;
  ```

  与 `matchesVoiceOption` 是同一套选项（`+100` / `-100` / `婉转声` / `粗嗓门`），却各写一遍；
  婉转声少了 `<= 100` 上界。当前 `voiceDb` 实测范围 -100~100，行为暂时等价，但 2026-10-05 那次
  「粗嗓门 = ≤-96 修正过宽」的修法在这里不会生效，下次再改口径必然漏改一处。
- **影响面**：目前无用户可见差异（脏数据 `voiceDb > 100` 时才会出现「婉转声命中」）；属于口径漂移风险。
- **修复建议**：删除 `matchesDemandVoice`，改为
  `voices/matchesVoiceOption` 的薄封装（`!voice || matchesVoiceOption(pet.voiceDb, voice)`）。
- **置信度**：高

  （`species.find` 193 行、`maleCapableOf(species)` 196 行）；调用方

## B1-M03 种公需求的「已接单」不会出现在导入后的结单提醒里（已修复 `968f424`）

- **等级**：中（功能遗漏；实现与「导入后提醒可结单」的口径不一致）
- **文件:行号**：[groupAutoPublish.ts:118-128](file:///d:/desk/洛克工具箱/src/ui/groupAutoPublish.ts#L118-L128)
  调用 [demandCriteria.ts:93-99](file:///d:/desk/洛克工具箱/src/domain/demandCriteria.ts#L93-L99)
- **问题描述**：提醒逻辑对每条 `status = 'claimed'` 的需求只调 `hasStockForDemand`。
  该函数第一步就是 `eggOfGameId.get(pet.gameId) !== criteria.eggGameId`，而种公需求的
  `eggGameId` 是负数蛋组 id（`-2 ~ -15`，见 `isStudDemandKey`），永远不相等 → 返回 false →
  种公需求被静默跳过。同文件 `eggNameOf` 也只收录蛋物种，种公需求拿不到名字（会退化成「蛋 -3」）。

  种公需求少了一条主路径。
- **修复建议**：在循环里按 `isStudDemandKey(demand.eggGameId)` 分流到
  `hasStockForStudDemand`；名字按蛋组显示（`蛋组 N`）。

## B1-L02 百分位只保留 1 位小数，95% 边界存在 <0.05 的舍入偏差

- **等级**：低（当前实际数据下几乎不会命中）
- **文件:行号**：[bodySize.js:33-37](file:///d:/desk/洛克工具箱/src/shared/bodySize.js#L33-L37)
  （`heightPercentOf` 的 `toFixed(1)`）、[parseBackup.ts:14-20](file:///d:/desk/洛克工具箱/src/domain/parseBackup.ts#L14-L20)
  （`weightPercentOf` 的 `Math.round(x*10)/10`）
- **问题描述**：合格判定比较的是四舍五入到 1 位小数的百分位：
  - 体重精确 94.96% 会被存成 95.0，被判成「≥95%」；
  - 身高精确 99.96% 会被存成 100.0，绕过 `HEIGHT_EXTREME_TOLERANCE = 0`，被判成「身高正好 100%」。

  实测 `heightCm` 来自抓包整数厘米（`core.js:1903`），图鉴身高区间按米保留两位，通常百分位台阶
  是 3.3% 以上，所以 99.96 这种值目前基本不可能出现；体重 94.96 这类边界则只在克级精确值上出现。
- **影响面**：极端边界下把「差一点」判成「达标」（或反过来）。当前属于理论偏差。
- **修复建议**：身高直接用厘米与区间端点比较（`heightCm >= size.max*100` / `<= size.min*100`），
  体重比较也用未取整的原始值；展示仍保留两位小数。
- **置信度**：中（偏差存在、可达性低）
