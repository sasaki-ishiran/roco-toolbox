## B9-M01 `MotherApiErrorCode` 缺后端已返回的 15 个码，`src/api` 用 `as` 断言把未知码硬塞进窄联合

- **等级**：中（违反同模块既有写法：错误码必须与后端穷举一致）
- **文件:行号**：
  `src/shared/motherGroups.ts:200-214`（`MotherApiErrorCode`）、
  `src/api/collectionGroups.ts:103`、`src/api/motherGroups.ts:157`（两处 `as MotherApiErrorCode`）、
  后端事实源 `functions/_lib/motherGroupsStore.ts:26-65`、`functions/_lib/motherGroups.ts:57-71`
- **问题描述**：
  共用契约里的错误码只列了 14 个：

  ```ts
  export type MotherApiErrorCode =
    | 'UNAUTHENTICATED' | 'NOT_MEMBER' | 'NOT_OWNER' | 'GROUP_NOT_FOUND' | 'GROUP_FULL'
    | 'INVALID_INPUT' | 'PAYLOAD_TOO_LARGE' | 'RATE_LIMITED' | 'REVISION_CONFLICT'
    | 'STALE_SOURCE' | 'SOURCE_MISMATCH' | 'GAME_ACCOUNT_ALREADY_SHARED'
    | 'OWNER_MUST_DISSOLVE' | 'INTERNAL';
  ```

  而后端 `MotherStoreErrorCode`（`motherGroupsStore.ts:26-65`）还包含
  `TARGET_CHANGED`、`TARGET_NOT_READY`、`TASK_TAKEN`、`TASK_ALREADY_COVERED`、`TASKS_NOT_CONFIRMED`、
  `TASK_NOT_FOUND`、`TASK_NOT_YOURS`、`DEMAND_UNSUPPORTED`、`DEMAND_NOT_FOUND`、`DEMAND_LIMIT`、
  `DEMAND_TAKEN`、`DEMAND_SELF`、`DEMAND_ALREADY_DONE`、`DEMAND_NOT_CLAIMED`、`DEMAND_NOT_YOURS`
  （15 个），全部经 `failCode` 原样写进响应体 `code`。

  两个 api 客户端把这 15 个码用断言吞掉：

  ```ts
  const code = typeof record.code === 'string' ? (record.code as MotherApiErrorCode) : 'HTTP_ERROR';
  ```

  `string → 字面量联合` 的断言 TS 允许，于是编译期不再提示"这里可能拿到未列出的码"，
  契约文件反而变成一份**过时的白名单**。B4 已给需求动作补了 `STORE_STATUS`（409/404/403），
  说明后端在按"每个码都有明确语义"演进，共用类型没跟上。
- **影响面**：
  - 当前不影响线上行为：UI 只用 `failure.message`（服务端中文文案）与 `failure.status`
    （`groupAutoPublish.ts:222` 判 409），没有按 `code` 分支。
  - 但任何后续按 `code` 做的事（差异化提示、是否允许自动重试、错误埋点、离线队列）都会漏掉
    需求承接/共同寻找的**全部**失败分支，且类型检查不会报错——例如「已被别人接了」
    （`DEMAND_TAKEN`）与「本组目标已更新」（`TARGET_CHANGED`）都会落到 `default` 分支。
- **修复建议**：
  1. 把 `MotherApiErrorCode` 扩成后端并集（纯类型改动，无运行时风险），顺序与
     `motherGroupsStore.ts:26-65` 对齐，避免下一次再漏；
  2. `src/api/*` 不再 `as`，改为 `isMotherApiErrorCode(value): value is MotherApiErrorCode` 守卫，
     未识别的码保留原字符串并落到 `'HTTP_ERROR'` 语义（或把 `MotherGroupsApiError.code` 放宽为
     `MotherApiErrorCode | (string & {})`），这样服务端新增码时前端不会静默归错类；
  3. 后端两处 `STORE_STATUS`（`motherGroups.ts:57-71` / `collectionGroups.ts:81-95`）建议共用一个
     `Record<MotherStoreErrorCode, number>`，现在两份枚举各自维护，已经有重复。
- **置信度**：高（类型与后端枚举可逐条核对）。

## B9-M02 前端仍把「需求键」当成唯一，归档表上线后同一键可同时有 done 行与新行：已结单计数会短暂倒退、二级页出现重复 React key

- **等级**：中（与 `docs/产品交互规范.md` 明确要求的计数口径冲突）
- **文件:行号**：
  `src/ui/useCollectionGroups.ts:381-398`（`mergeDemand`）、`src/ui/useCollectionGroups.ts:415-437`（`withdrawDemand` 的乐观删除）、
  `src/ui/MotherGroupResources.tsx:753-762`（`myDemandsByEgg` 不过滤 done）、`MotherGroupResources.tsx:927-933`（需求键）、
  `MotherGroupResources.tsx:2355-2367`（`key={demandKey(demand)}`）、
  `MotherGroupResources.tsx:1102-1106`（允许重发已完成键）、`src/domain/demandStats.ts:9-18`；
  服务端事实源 `functions/_lib/collectionGroupsStore.ts:1556-1596`（归档行与新行一起返回）、
  `functions/migrations/2026-10-29-collection-demand-completions.sql:7-8`（"完成时把整行搬到归档表，
  因此同一颗蛋结单后可以再次发布"）
- **问题描述**：
  新归档表让「同一需求键」可以同时存在两条记录：一条 `status='done'`（历史），一条新的
  `status='open'`（重发）。接口把它们一起返回：

  ```ts
  // collectionGroupsStore.ts:1593-1595
  return [...activeRows.map(toDemand), ...completedRows.map(toCompletedDemand)].sort(
    (a, b) => b.updatedAt - a.updatedAt,
  );
  ```

  而重发在 UI 上是**被明确允许**的：`missingPublishItem` 只在 `status !== 'done'` 时把性格算作
  "已发过"，其余都放进可发列表（`MotherGroupResources.tsx:1102-1123`）。于是：

  1. 需求方把「蛋 X / 固执 / 母 / 大块头 / +100」结单后再发同一键，`addDemand` → `mergeDemand`
     按五元组过滤列表，**把那条 done 归档行一起顶掉**：

     ```ts
     setDemands((list) => [
       next,
       ...list.filter((item) => !(item.demanderAccountId === next.demanderAccountId
         && item.eggGameId === next.eggGameId && item.nature === next.nature
         && item.gender === next.gender && item.body === next.body && item.voice === next.voice)),
     ]);
     ```

  2. 撤回同一键时 `withdrawDemand` 的乐观删除用的也是五元组，同样会删掉 done 行。
  3. 两处的后果都是 `completedDemandCounts(demands)`（`demandStats.ts:9-18`）少 1，
     成员行与需求中心的「已结 N 单」在**下一次轮询（`POLL_INTERVAL_MS = 15_000`）之前**少 1，
     轮询回来后自动恢复——属于自愈型错误，但正是规范里写死不许的事：
     `docs/产品交互规范.md:229-230`「已结单 = 本组内 `status = done` 且承接人是该成员的需求条数（**全时段**）；
     已完成的需求不可撤回，否则计数会倒退」。
  4. `myDemandsByEgg` 不过滤 done（`MotherGroupResources.tsx:755`），二级页「我的需求」会把 done 行与
     active 行同时渲染，两者 `key` 都是 `${demanderAccountId}:${demandKeyOf(demand)}` →
     **React 重复 key**；`confirmWithdraw === key` / `confirmComplete === key` 也被两条共用，
     点其中一条会让另一条一起进入"确认撤回"状态（`MotherGroupResources.tsx:2425-2457`）。
     顺带「我的需求 · N」把已完成也计进了条数（`MotherGroupResources.tsx:2348`），与"我的需求"的直觉口径不一致。
- **影响面**：
  触发条件：需求方对同一颗蛋、同一性格、同样性别/体型/声音，先结单、再发一次需求（用户拿到蛋后
  再要一只同款是最常见场景）。用户看到：
  - 成员行 / 需求中心的「已结 N 单」闪一下变小（≤15s 后自己恢复）；
  - 二级页「我的需求」出现两条一模一样的条件，其中一条标「已完成」；
  - 点「撤回」时两条同时进入确认态，React 开发构建报 duplicate key 警告。
- **修复建议**（不需要改协议字段，纯前端 + 可选服务端补字段）：
  1. 给本地列表一个能区分两条的标识：done 行用 `${demandKey}@done:${updatedAt}`，active 行用
     `${demandKey}@active`；`mergeDemand` / `withdrawDemand` 只按 **active** 标识匹配
     （即 `mergeDemand` 过滤条件加 `item.status !== 'done'`，`withdrawDemand` 同理），
     React `key` 与 `confirmWithdraw`/`confirmComplete` 也换用这个标识；
  2. 若第 1 步嫌 key 太脆，让服务端在 done 行补 `completedAt`（或 `completionId`）字段，
     前端用它做去重标识——但这属于改接口，按纪律先停下确认，不在本轮动；
  3. 「我的需求 · N」建议只数 `status !== 'done'`，或拆成「进行中 N / 已完成 M」。
- **置信度**：中高。服务端行为与前端代码路径已逐行确认；"计数短暂倒退"的实际观感依赖轮询时序，
  未在真机复现（本批只读，未跑 Playwright）。

## B9-U02 家园增量的 opcode 1044 与 1043 共用一套结构、负数标量会被当成 64 位无符号：两处都缺协议依据

- **等级**：不确定（需采集端协议负责人确认）
- **文件:行号**：`home.js:350-357`（`opcode === 1043 || opcode === 1044` 走同一个 `deltaHome`）、
  `home.js:17-33`（`readVarint` 不做 int32/int64 两补码还原）、`home.js:79-82`（`firstInt` 只接受 `typeof === 'number'`）、
  `home.js:110-121`（`positionOf` 任一坐标缺失即返回 `null`）
- **问题描述**：
  1. `decodeHomePayload` 把 1044 与 1043 当同一结构处理（进入在 `action.1`、离开在 `action.2`）。
     这来自"移植自采集器 1.2.6"的假设，仓库内没有 1044 的报文样例或字段表可以佐证；
  2. protobuf 的负 `int32` 会编码成 10 字节 varint（高位全 1），`readVarint` 会把它读成
     `> Number.MAX_SAFE_INTEGER` 的 BigInt 并转成字符串，`firstInt` 因此返回 `null` → `positionOf`
     返回 `null` → 坐标整块丢失（`position` 字段缺省）。家园坐标如果是"房间内相对坐标"，出现负值并不奇怪，
     目前 5 条用例里的坐标全是正数，覆盖不到这个分支。
- **影响面**：1044 若结构不同，会解析出错误的住户/蛋增减（比 1043 更隐蔽：`changed = false` 时只是静默丢掉）；
  负坐标只影响"哪个窝/哪一层"的展示，不影响母本/配对判定。
- **修复建议**：向采集端要一份 1044 的真实 payload（脱敏）核字段；`firstInt` 增加
  `signed` 参数（`value > 2^63` 时按 `value - 2^64` 还原），或统一用 `BigInt.asIntN(64, value)` 后再生效。
- **置信度**：低-中。**需要谁确认**：安卓采集端（`CaptureController` / 1.2.6 字段表）负责人。
