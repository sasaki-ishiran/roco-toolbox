## B4-H01 母本发布请求体上限对折到 128KiB，与新增 `lines` 字段和声明上限不匹配，多账号用户会 413 / 发布不可用

- **等级**：高（触发条件依赖账号数据量，见下方阈值表）
- **文件:行号**：
  [collectionGroups.ts:334-340](file:///d:/desk/洛克工具箱/functions/_lib/collectionGroups.ts#L334-L340)、
  [shared/motherGroups.ts:44-49](file:///d:/desk/洛克工具箱/src/shared/motherGroups.ts#L44-L49)、
  [shared/motherGroups.ts:69-72](file:///d:/desk/洛克工具箱/src/shared/motherGroups.ts#L69-L72)、
  客户端预检 [motherResource.ts:163-197](file:///d:/desk/洛克工具箱/src/domain/motherResource.ts#L163-L197)、
  自动发布 [groupAutoPublish.ts:174-218](file:///d:/desk/洛克工具箱/src/ui/groupAutoPublish.ts#L174-L218)
- **问题描述**：
  本次把 `/api/collection-groups/:id/resources/me`（小组页实际使用的发布口）的读体上限从
  「两种组都用 `STUD_RESOURCE_MAX_BODY_BYTES` = 256KiB」改成「母本组用
  `MOTHER_RESOURCE_MAX_BODY_BYTES` = 128KiB」：

  ```ts
  const parsed = parseCollectionPublishBody(
    await readJsonBody(
      request,
      group.groupType === 'stud' ? STUD_RESOURCE_MAX_BODY_BYTES : MOTHER_RESOURCE_MAX_BODY_BYTES,
    ),
    group.groupType,
  );
  ```

  与此同时母本摘要新增了 `accounts[].lines`（每账号最多 1024 条 × 每条最多 30 个性格），
  **上限减半与载荷变大发生在同一批改动里**。而声明上限彼此矛盾：`MOTHER_RESOURCE_MAX_ACCOUNTS = 50`、
  `MOTHER_RESOURCE_MAX_EGGS_PER_ACCOUNT = 1024`、`PRODUCTION_LINE_MAX_PER_ACCOUNT = 1024`，
  这些上限对应的 JSON 体积远超 128KiB（估算过程见文末附录 A）。
- **影响面**：
  - 手动发布：客户端 `assertMotherResourceWithinLimits` 先在本地拦下，用户看到
    「共享资源约 N KiB，超过 128KiB 上限；请减少共享账号后重试」——即符合 changelog
    2026-10-28「共享全部母本与产线」的用户**被要求少共享几个号**，没有别的出路；
  - 服务端直拒：绕过本地预检（旧客户端 / 换机）时 `readJsonBody` 抛 `PAYLOAD_TOO_LARGE` → 413；
  - 自动发布：`groupAutoPublish` 一次发布**全部本机账号**（`baseKeys` 为空时 `keys = localKeys`，
    第 205-206 行），失败被第 183 行 `catch {}` 吞掉 → 用户看不到任何提示，组员那边该成员的
    资源永远停在旧版本（表现为「需更新」但不自动恢复）。
- **修复建议（需要业务决策，先别动手）**：
  1. 立刻可做（不改语义）：把母本发布口的上限提到 256KiB（或 `Math.max(STUD, 2 * MOTHER)`），
     与旧行为一致，先把回归挡住；
  2. 中期：让上限与声明上限自洽 —— 要么把 `PRODUCTION_LINE_MAX_PER_ACCOUNT` 降到 128KiB 能装下的数量
     （≈700 条/账号时仍只够 1 个号），要么把发布拆成「按账号分批」的多次写入
     （store 侧需要支持「合并写入单账号」而不是整份替换，属 B3）；
  3. `groupAutoPublish` 的 `catch {}` 至少要把 `PAYLOAD_TOO_LARGE` 冒泡成可提示的失败（B6）。
- **置信度**：中高（体积算术可证；是否已在线上触发取决于真实账号规模 → **待用户决定**：需要线上
  最坏请求体的实测值）

## 附录 A：128KiB 与 `lines` 的体积估算过程

用 `node` 对真实 JSON 形状取 `Buffer.byteLength(utf8)`（性格名按 2 个汉字 = 6 字节算）：

| 对象 | 实测字节 |
| --- | --- |
| 单条 line，1 个性格（`eggGameId` 4 位） | 56 B |
| 单条 line，6 个性格 | 101 B |
| 单条 line，10 个性格 | 137 B |
| 单条 line，30 个性格（`PRODUCTION_LINE_MAX_NATURES` 上限） | 317 B |
| 单账号固定开销 + 200 个蛋 id（无 lines） | 1,118 B |
| 单账号 200 条产线 × 5 个性格 | 19,728 B |

线性拟合（蛋 id 4 位时）：**单条 line ≈ 47 + 9 × 性格数**（蛋 id 每多一位 +1 B；每个蛋 id ≈ +5 B）。

上界依据：`catalog.gen.json` 里可孵蛋组的蛋物种 = 200 个 → 单账号产线理论上限
= 200 蛋 × 4 档 = **800 条**（低于常量 1024）。

| 账号形态 | 1 个账号 | 2 个账号 | 3 个账号 |
| --- | ---: | ---: | ---: |
| 200 产线 × 5 性格 | 19.7 KB | 39.4 KB | 59 KB |
| 400 产线 × 8 性格 | 47.6 KB | 95 KB | **143 KB ← 413** |
| 800 产线 × 8 性格（单号理论上限） | 95 KB | **190 KB ← 413** | — |
| 1024 产线 × 10 性格（常量上限） | **140 KB ← 413** | — | — |
| 最省形态：1024 产线 × 1 性格 + 1024 蛋 id | ≈ 65 KB | ≈ 130 KB **← 413** | — |

结论：
1. 声明上限（1024 条/账号、50 个账号）与 128KiB 在数学上不可能同时满足 —— **单账号**按常量上限就能写超；
2. 最保守的「满 1024 条产线」形态下，**2 个账号**即越界；
3. 真实的重度收集者（≥400 条产线/号、8~10 个性格/条）**3 个账号**越界；
4. 改动前同一请求口是 256KiB 且没有 `lines` 字段，因此这是**本批引入的回归风险**，不是旧问题。
   线上实际最坏请求体大小无法静态确认 → 见「待用户决定」第 1 条。
