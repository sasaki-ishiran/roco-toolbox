  需求行通过「(group_id, demander_account_id) → mother_group_members」外键挂在成员行上，且是 `ON DELETE CASCADE`：

  ```sql

  FOREIGN KEY (group_id, demander_account_id)
    REFERENCES mother_group_members (group_id, account_id) ON DELETE CASCADE
  ```

  ```ts

  …

    statements.push(db.prepare(
      `DELETE FROM collection_group_demands
  ```

  外键开启时（D1 默认强制外键，见 U01），第 4 条语句删成员行的那一刻，该成员**作为需求方**的全部需求行

  2. A 自己退出，或组长移除 A（规范 237-238 明确要求「已完成的接单记录保留」，

  3. 需求中心「其他人接的」里 **B 名字后的已结单数 -1**；B 之前「已结单 N 单」的历史凭空少一条。
  同一根因还会在「账号注销」时触发（`mother_group_members.account_id` 也是 `accounts ON DELETE CASCADE`）。
  与 `demandStats.ts:7` 的注释「他被移除后当年结的单仍计入承接人的累计」直接冲突。

- **修复建议（需要 schema 变更，属「待用户决定」，先别动手）**：
  - **方案 A（推荐）**：把「已结单」从需求行里解耦——新增
    `collection_group_completions(group_id, claimer_account_id, demander_account_id, egg_game_id, nature, gender, body, voice, completed_at)`，
    `completeCollectionDemand` 在把需求置 done 的同一批里插入一行归档；`listCollectionDemands` 保持现状，
    另加一个只读归档的聚合（或直接在同一个响应里返回 `completions`）。成员/账号删除都不影响累计。
  - **方案 B**：成员行软删除（`mother_group_members` 加 `left_at`），不再物理删行——保住外键目标，
    `readCollectionGroupDetail` / `listCollectionTasks` 过滤 `left_at IS NULL`。改动面大（所有成员查询、20 人上限）。
  - **方案 C（不改 schema 的临时兜底）**：至少把 968-975 那条无效 DELETE 挪到删成员行**之前**，
    并把「移除/退出会连带删掉其已完成的单」写进已知限制与测试；这只能保证语义诚实，不能保住计数。
  - 提醒：`motherGroupsStore.ts:302-304`（旧 `/api/mother-groups` 退出路径）有同样的级联，修的时候一并覆盖。
- **置信度**：0.85（代码路径与约束都确认；唯一不确定是 D1 是否强制外键，见 U01。即使外键关闭，
  done 行会变成「需求方已不是成员」的孤儿行，仍属数据正确性问题，只是症状从「计数倒退」变成「幽灵单」）

## B3-M03 发布额度是「先查后写」：并发发布可越过成员 / 小组上限，且每个性格都单独查一次

- **等级**：中
- **文件:行号**：
  [collectionGroupsStore.ts:1623-1691](file:///d:/desk/洛克工具箱/functions/_lib/collectionGroupsStore.ts#L1623-L1691)（额度判定
  [1639-1669](file:///d:/desk/洛克工具箱/functions/_lib/collectionGroupsStore.ts#L1639-L1669)）
- **问题描述**：
  先并行查 N 次是否已存在（1639-1642）→ 再查「组内非 done 总数」（1645-1652）→ 再查「本人非 done 总数」
  （1655-1663）→ 最后 `INSERT … DO NOTHING`（1672-1685）。额度判定与插入之间没有任何原子性：
  两台设备同时发布（或一次请求里 6 个性格 + 一次重试交错）都能各自算到「还没超」，于是整组 / 单人超额。
  另外一次发布最多要做 `6 + 2 + 6 = 14` 次 D1 往返，其中 12 次是同一张表按主键的重复查询（1640、1688），
  插入完成后还要再查一遍才拿到行（1687-1690）。
- **影响面**：额度是防刷屏的软约束，超额只会让组内需求列表更早变长（配合 M04 放大响应体），
  不会破坏需求本身的正确性；用户侧看不到错误，只是别人更难发需求。
  性能上是典型的 N+1（上限 6，代价可控，但与「一次 batch 拿回结果」的既有写法不一致）。
- **修复建议**：
  - 额度改成「插入后复核」：`INSERT … DO NOTHING RETURNING …` 拿到真正插入的行，
    再用一条 `SELECT COUNT(*)` 复核；超限时把本次插入的行删回去并返回 `DEMAND_LIMIT`（D1 支持
    `RETURNING`，同文件 302-317 已在用 `RETURNING group_id`）。
  - 或者用条件插入：`INSERT … SELECT … WHERE (SELECT COUNT(*) …) + ? <= ?`，让 SQLite 单语句保证上限
    （与 `joinCollectionGroup` 的满员写法同构，依据：参照 `collectionGroupsStore.ts:302-317` 既有写法）。
  - N+1 部分：把「查是否已存在」与「取回结果」合并成一次 `SELECT … WHERE group_id = ? AND demander_account_id = ? AND egg_game_id = ?`
    再在内存里按 7 元组匹配（或直接用 `RETURNING`），14 次往返可以降到 3 次。
- **置信度**：0.85（并发窗口确定；实际超额幅度受 WRITE_LIMIT 限流压制，影响可控，所以定中不定高）

## B3-M04 需求列表既无上限也无分页，而 `done` 行永不清理

- **等级**：中
- **文件:行号**：
  [collectionGroupsStore.ts:1534-1547](file:///d:/desk/洛克工具箱/functions/_lib/collectionGroupsStore.ts#L1534-L1547)、
  [1645-1663](file:///d:/desk/洛克工具箱/functions/_lib/collectionGroupsStore.ts#L1645-L1663)、
  索引 [schema.sql:196-197](file:///d:/desk/洛克工具箱/functions/schema.sql#L196-L197)
- **问题描述**：

  ```ts
  /** 组内全部需求（不分状态），按更新时间倒序。 */
  export async function listCollectionDemands(db, groupId) {
    … `SELECT ${DEMAND_COLUMNS} FROM collection_group_demands
        WHERE group_id = ? ORDER BY updated_at DESC` …
  ```

  - 没有 `LIMIT`、没有游标分页，一次返回该组**历史全部**需求行；
  - `DEMAND_LIMIT_PER_GROUP = 200` 只约束 `status <> 'done'`（1645-1649），
    `done` 行不占额度、也不被任何路径清理（撤回被禁止、移除成员反而删掉、见 H01）——
    于是 done 行随时间**只增不减**；
  - `ORDER BY updated_at DESC` 没有索引支撑：`collection_group_demands` 只有主键
    `(group_id, demander_account_id, egg_game_id, nature, gender, body, voice)` 和
    `idx_collection_group_demands_claimer (group_id, claimer_account_id)`，按 group 取全量后要在内存里排序。

  量级估算：单行 JSON ≈ 150–200 B；一个活跃 20 人组一年结几百单，5,000 行时单次响应 ≈ 0.8–1 MB，
  且 `GET /demands` 在每次进入小组、每次需求动作后都会重拉（前端还会整份算「已结单数」）。
- **影响面**：小组用久了需求中心越拉越慢、流量变大（移动端明显）；D1 每次读的行数也线性增长。
  功能不会立刻出错，所以定中；若某组 done 行累积到数千，建议升级为「高」。
- **修复建议**（不改 schema 的两步）：
  1. 服务端加 `LIMIT`（例如 500）+ `before`（updated_at + 复合键）游标，按状态分组返回
     （前端只需要「未完成全部 + 最近 N 条已完成」）；
  2. 若「已结单」改成独立计数（H01 方案 A），需求列表就可以完全不含 done 行，问题自然消失。
  索引建议只记录（禁改 schema）：`CREATE INDEX … ON collection_group_demands (group_id, status, updated_at)`
  可同时支撑「按组 + 状态」过滤与排序。
- **置信度**：0.9（无 LIMIT / 无索引是确定事实；「算不算明显性能问题」取决于线上组规模，需产品确认预期留存）
